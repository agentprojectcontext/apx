An extension is a folder with an `apx-extension.json` that brings several things together: skills, MCP servers,
routine templates, the secrets they need and, optionally, a sandboxed plugin. APX reads the manifest without running
anything: adding it copies its files and runs nothing, and connecting it approves exactly the files it had.

## Find them in the Marketplace

**Marketplace**, in the sidebar (the store icon), is where extensions are found, added and connected. Everything you
add to your agents is an **extension**; a label says where it comes from: **Included** (it comes with APX: Google,
Asana, the channels, the browser), **Official** (APX publishes it, with those exact files), **Third party** (another
catalog, a file or an address someone gave you) or **Yours** (a folder you built, or a server you added by its address
here). Official shows as a check after its name, Included and Yours as a small word, and Third party with no
mark: the line under its name says where it comes from. What an extension brings (an MCP server, skills, agents,
routines, a device's app) is inside it. Resources keeps the technical parts (Skills, MCP, Variables): an MCP server
you write there by hand stays a server of yours there and is not listed in the Marketplace.

<Shot name="marketplace" alt="The Marketplace's Explore: search, filters by kind and extensions by category, each with its label and one button" caption="Marketplace › Explore" />

- **Explore** has search and filters on top (**All**, **Integrations**, **Connectors**, **Channels**, **Skills**,
  **Agents**; a filter with nothing in it is not shown), then **New** (while only a few are new), every category in
  compact rows (the ones included with APX in theirs, marked **Included**) and **Channels** together. Each row has its
  icon, name and label, one line, and under it what it is and who from ("Connector · From APX") with small icons for
  what it brings and how many (a plug for its connector, a book for its skills, a bot for its agents, a phone for a
  device's app; hover one to read it). What it is comes from
  what it brings: a **Channel** APX talks through; an **Integration** with code or an app of its own (a **Native
  integration** when APX makes it, like Google Calendar); a **Connector**, an MCP server (with skills to use it or
  not); **Agents**; or **Skills** alone. Each row has one button: **Add** (it opens the extension's page and adds it
  there), or **Connect** for one included with APX.
- **Your extensions** lists what you added, in two groups: **Needs attention** (not connected yet, a new version, an
  error) and **Active**. The same groups show in the left column. Channels are found and connected from Explore, but
  live in **Channels**, so they are not repeated here.
- An extension's page has one button that follows its state: **Add** → **Connect** (or **Pair** for a device's app)
  → **Connected ✓**. Turn off, update, go back a version, settings and remove are in **⋯**.
- **Add** and **Connect** are two steps you take on the page. **Add** checks its files (from APX's catalog they must
  be the ones APX publishes) and copies them; nothing runs. The page stays, now marked added, with **Connect** as its
  button. **Connect** (or **Pair**) opens a box with APX joined to the service, the keys to type, a sign-in or the
  device's code (for one you sign in to, it says first that your browser opens on the service's sign-in page), and what
  you approve written above the button; it is your decision that it works. **Later** closes
  the box and leaves you on the page. Once connected, it shows the tools its server answered with. One with nothing to
  connect is ready as soon as you add it.
- The page shows everything it brings before you add it, the same as after: things to ask it, about it, and **What
  it brings**: each **Connector** with its address (with a copy button), how it signs in and its tools (by name when
  its page names them; otherwise "You'll see them when you connect it"); its **Skills**, each with what it does, or
  that it brings none; its ready-made **Agents** (each with **Add agent** once added), **Routines** (each with **Add to
  Routines**), widgets and the app for a device; and what **It will ask you for**: its keys and the settings it needs.
  Beside it: developer, version and date, **Security and access** ("Can send data to api.hubapi.com", "Runs code on
  your computer", files nobody verified), **Authorization** ("A key of yours", "You sign in to the service"), what it
  needs and does not do, cost, privacy, links and its fingerprint under **Details**. A fact nobody gave is not shown.
- **Add** › **From an address** or **From a file** adds something that is not in a catalog: the same box opens under
  a picker (a file, an address or a folder). An address of an `.apxext` is read as a package; any other https address
  is an MCP server: APX adds it as an extension of yours with that server inside and connects it right away.
- When it can't be added, the box says why: the download failed, the files changed since you looked at them, they are
  not an extension, or it needs a newer APX.
- When you have added catalogs, Explore has a **catalog** picker (all, APX's, or one you added), each with how many
  it lists; each filter and the list above it say how many they show. An extension from another catalog says who
  makes it ("From Anthropic"), else the GitHub account its code lives under ("From acme on GitHub"), else "Third
  party". Only what APX publishes with those exact files is Official.
- Another catalog's extensions go in APX's categories, beside APX's own (Claude's "database" and "monitoring" in
  Data, "security" or "testing" in Development, "design" in Design and media…); one whose category fits none of them
  stays under its catalog's name, after the categories.
- One service is listed once. When another catalog offers something APX already includes or publishes (the same id,
  the same name, or the same website), Explore and search show APX's, and its page lists the other one under
  **Another version**, with the catalog it comes from; that one's own page points back to APX's.
- Removing an extension or a catalog, or disconnecting an account, always asks first. In **Advanced**, APX's catalog
  has a lock (it is always there) and says how many it lists; **See in Explore** shows only one catalog's extensions.
- **Advanced**, at the bottom of the left column, is for building and trying extensions: catalogs, installing from a
  file or a folder, writing an MCP server by its command (it is saved in **Resources › MCP**), and the guide to build
  one.

APX reads what each catalog package brings from the package itself: it downloads it once, checks it against the
catalog's sha256 and fingerprint, and keeps only its manifest, its listing and its images in its home. Nothing is
added or run until you add it. APX ships a copy of the official catalog, so the Marketplace lists it offline.

## Do you need one?

Start with the smallest thing that does the job:

| You want | Make |
|---|---|
| Know-how for one project's agents | A [project skill](/extend/skills/) in `.apc/skills/` |
| One more MCP server for your agents | `apx mcps add` (see [MCP servers](/extend/mcp/)) |
| Skills, servers and routines that travel together, shared or reused | **An extension** |
| Code that watches events or adds context to your turns | An extension with a plugin |

## A real example: daily brief

APX's repository ships `examples/extensions/daily-brief`: one skill and a weekday routine that uses it.

<FileTree>
- daily-brief/
  - apx-extension.json
  - skills/
    - daily-brief/
      - SKILL.md
</FileTree>

```json title="apx-extension.json"
{
  "id": "daily-brief",
  "name": "Daily brief",
  "version": "1.0.0",
  "description": "A short morning brief: open tasks, what is due, what others owe you.",
  "skills": "skills",
  "routines": [
    {
      "name": "Morning brief",
      "schedule": { "kind": "cron", "cron": "30 8 * * 1-5" },
      "prompt": "Use the daily-brief skill to write my morning brief."
    }
  ]
}
```

The skill tells the agent to read your open tasks and commitments, write at most eight lines, and answer `SKIP` when
there's nothing worth saying (a routine that answers `SKIP` tells nobody).

## The manifest

The schema is strict: unknown keys are refused.

| Field | What it holds |
|---|---|
| `id` | Lowercase letters, digits, `_` and `-`, up to 20 characters. |
| `name`, `version` | Required. `description` is optional, up to 500 characters. |
| `min_apx` | Optional: the oldest APX that runs it (`"2.18.0"`). An older APX says it needs that version instead of adding it; a key an APX does not know is read the same way. |
| `skills` | A folder of skill folders, each with its `SKILL.md`. |
| `mcp` | Servers by name (letters, digits and `_`): `command` + `args` + `env`, or `url` + `headers`. A command starting with `./` runs from the extension's folder. |
| `routines` | Templates with a `name`, a `schedule` (`cron`, `every` N minutes with N of 5 or more, or `once`) and a `prompt`. |
| `secrets` | Up to 10, each with a `name`, a `label` and an optional `url` where to get it. You type each value once. |
| `plugin` | Optional code; see below. |

An MCP server in an extension can only use the extension's **own** secrets, as `secret://name`. It can't name your
other variables or the environment, so a bundle can't carry your credentials elsewhere.

```json title="An MCP server with its own secret"
"mcp": {
  "crm": { "command": "node", "args": ["./server.mjs"], "env": { "CRM_TOKEN": "secret://token" } }
},
"secrets": [{ "name": "token", "label": "CRM API token", "url": "https://example.com/settings/tokens" }]
```

### Manifest 2

`"manifest": 2` adds what a bigger extension needs. A manifest without it reads as before.

| Field | What it holds |
|---|---|
| `settings` | Values the owner sets, with a `type` (`string`, `number`, `boolean`, `directory`, `file`), a `label`, optional `description`, `default`, `options` (a choice), `required`. A `sensitive` one goes to the secret store and is referenced as `secret://name`; a plain one is referenced as `setting://name` in its servers' arguments, environment, address or headers (in an address, `setting://address/api` drops a final `/` the owner typed). `"generate": "random"` (sensitive strings only) makes APX fill a random key at install. |
| `agents` | Ready-made agents (`id`, `name`, `description`, `prompt`) the owner adds from its page. |
| `pages` | Its own HTML pages (`id`, `title`, `entry`), opened from its settings in a sandboxed frame with no network. A page reads and sets only its own settings through `window.apx` (`settings.get`, `settings.set`, `secrets.has`, `secrets.set`, `close`). |
| `apps` | Widgets or apps (`.apxart` files) the owner adds to Apps from its page. |
| `hosts` | The hosts its code connects to, shown before it is turned on. |
| `platforms` | The systems it runs on (`darwin`, `linux`, `win32`); it does not turn on elsewhere. |
| `companion` | An app on another device: `name`, `platform` (`android`, `android-tv`, `ios`, `macos`, `windows`, `linux`), the app `file` in the package or a store `url`, `steps`, and `pairing`: `{ "with": "apx" }` pairs it with APX as a device (a code and QR), `{ "with": "extension", "server", "tool" }` asks the extension's own tool for the code. |

### Its page: `apx-listing.json`

An optional `apx-listing.json` beside the manifest is its page in the Marketplace: a `summary` and `tagline`, a
Markdown `description`, `prompts` to try, `requirements`, `limits`, `pricing`, `privacy`, an `icon` and `screenshots`
in the package, `links`, and Spanish text under `locales.es`. Its `tools` (`name` and an optional `description`)
name what its connection brings, so the owner sees them before adding it; without them APX says the service decides
its tools and shows the real ones once it is connected.

Nothing an extension brings is added by itself: its agents and apps wait for **Add**, its companion app for
**Pair**. Its settings, pages, agents and apps show on its page in the Marketplace, or with `apx extensions` in the
terminal; `apx extensions set <id> name=value` sets them (`name=-` reads a sensitive value from stdin).

An agent you add from an extension is one of yours, and its button then reads **In your team**. Removing the
extension archives the agents you added from it (the confirmation names them); you can bring each back or delete it
for good in **Config › Agents**. One that answers a channel stays until you choose who answers it in **Channels**.

## Install it

An extension comes as a folder, as an **`.apxext` file** (the folder zipped; the packages APX publishes come this way)
or from an **https address** of one. APX shows what it brings before it writes anything; adding it runs nothing until
you connect it.

<Tabs>
<TabItem label="Panel">

<Steps>

1. Double-click an `.apxext` file, or drop it on the APX window. Or open the **Marketplace** and press
   **Add** › **From a file** (**Advanced** also adds from a folder).

2. Look at what it brings: its tools, skills, agents and routines, where it connects, the keys it asks for, whether
   it runs a program on your computer and whether it is **Official** or **Third party** (below). Then **Add**.

3. Its page opens, added. Press **Connect**, type its keys (or sign in, or pair the device) and press **Connect**
   again. One with nothing to connect is ready as soon as you add it.

4. Its routines are suggestions: **Add to Routines** puts one in Routines, turned off until you turn it on.

</Steps>

</TabItem>
<TabItem label="Terminal">

```bash
apx extensions inspect ~/work/daily-brief                          # what it would bring; nothing is installed
apx extensions install ~/work/daily-brief                          # a folder, copied in, off
apx extensions install ~/Downloads/daily-brief.apxext              # a file on this computer
apx extensions install https://example.com/daily-brief.apxext      # a download (https only)
apx extensions pack ~/work/daily-brief                             # one file to share: daily-brief-1.0.0.apxext
apx extensions set daily-brief region=eu                           # its settings (name=- reads a sensitive one from stdin)
apx extensions secret <id> <name>                                  # a declared secret's value, on stdin (--clear removes it)
apx extensions on daily-brief
apx extensions rollback daily-brief                                # back to the version installed before
apx extensions                                                     # installed ones, on or off
apx extensions off daily-brief
apx extensions rm daily-brief
```

An `.apxext` given to the terminal is read on the terminal's computer and sent to the core, which may run elsewhere;
a folder is read where the core runs.

</TabItem>

Installing copies plain files into APX's home and fingerprints them. If the installed copy changes on disk, APX turns
the extension off at its next start until you approve it again. To take changes from the original folder or address,
install it again or use **Read again** / **Download it again** in its settings (**⋯ › Settings**).

### What an `.apxext` may hold

It is a plain zip of the extension's folder: `apx-extension.json` at the top, or inside one top folder (how zipping a
folder by hand packs it). APX refuses the whole file, before writing anything, when it holds a link, an encrypted
entry, a path that leaves the folder (`..`, an absolute path), sizes that don't match what unpacks, two names one disk
would take as one, more than 2,000 files or more than 50 MB unpacked. The file itself is at most 20 MB. `.git`,
`node_modules`, and what a Mac adds when zipping (`__MACOSX`, `.DS_Store`, `._` files) are left out.

`apx extensions pack <folder>` makes one for you: it checks the folder first, leaves the same things out, and the same
folder always packs into the same file (`<id>-<version>.apxext`). To turn a script or an app you already have into an
extension, see [Bring your app to an extension](/extend/app-to-extension/).

### Official or third party

APX compares the extension's fingerprint (the same one turning it on approves) with APX's official catalog. It is
**Official** when the catalog lists that id and version with exactly those files; anything else, including an official
package with one byte changed, is **Third party**. Nothing is signed: what decides is that the files match the ones APX
publishes. APX asks for the catalog only when you inspect or install an extension, keeps it in its home, and uses that
copy when it can't reach it; with no copy, the dialog says it couldn't tell. A different catalog address can be set
with `APX_MARKETPLACE_INDEX` ([Configuration](/reference/configuration/)).

### Your own catalogs

**Advanced › Add catalog** (or `apx extensions catalogs add <source>`) adds a list of extensions for yourself: a GitHub
`owner/repo`, a git address, an https address of an index, or a folder. Suggested ones (Anthropic's Knowledge Work and
Claude plugins) are one click away. Everything from them is **Third party**; APX's own catalog always stays.

- APX reads its own index format and Claude Code's `.claude-plugin/marketplace.json`. A Claude plugin installs turned
  into an extension: its skills, its MCP servers (from `.mcp.json`, with or without `mcpServers`, or the file its `plugin.json` names), its `agents/`
  as ready-made agents, its license and readme. A `${VAR}` in a server becomes a setting you fill in once: a key when
  its name says so (`KEY`, `TOKEN`, `SECRET`…), otherwise a plain value, with `${VAR:-default}` as its default. A server
  whose address you type says so before you turn it on. Commands and hooks have no APX counterpart and are left out.
- What each plugin brings is read with the catalog, the way installing converts it, so it shows as what it is before
  you add it (a plugin with an MCP server is a **Connector**). A plugin that would bring only what APX has no counterpart
  for (commands, hooks, language servers, output styles) is left out, since it would add nothing. For a plugin kept in another repository APX reads only its server files at its
  commit, so it shows as a Connector when it has one; whether it also brings skills or agents shows once added. A
  catalog read before this shows it after **Read again**.
- A plugin from another repository counts only pinned to a commit (`sha`); it is read at that commit.
- Each plugin's license is read before it is listed (its own, else its repository's). Only licenses that allow a copy
  (MIT, Apache-2.0, BSD, ISC, MPL-2.0, Unlicense, CC0, 0BSD) are converted; the rest are left out. Its row in
  **Advanced** lists what was left out and why (`apx extensions catalogs` too: `license`, `unpinned`, `source`,
  `invalid` or `empty`).
- APX keeps the commit each catalog was read at; **Read again** takes its newest.
- In the panel a catalog is read in the background: you can close the dialog and keep working. Its row in
  **Advanced** says how far along it is (a big Claude catalog checks each plugin's license and can take a minute), and
  its extensions show up in Explore once it is read. If it can't be read, the row says so with **Try again**. The
  terminal waits until it is read and prints what it lists.
- From the terminal, `apx extensions catalog` prints each entry's address (`catalog:<catalog>/<id>`), which
  `apx extensions inspect` and `apx extensions install` take.

### Updates and going back

Installing another version of one you have keeps the one before beside it. The dialog shows what the new version adds
(a server, a host it connects to, a secret, a routine, what its plugin may reach) and what it drops.

- An extension that is on **stays on** only when the new version is official and asks for nothing more.
- Otherwise you connect it again to approve what it adds; until then it is off, and its card lists what it adds.
- **⋯ › Back to 1.0.0** (the version kept) swaps it with the version kept before, each as you had approved it (on or off). Pressing it
  again goes forward.

## Plugins

When files aren't enough, an extension can bring a plugin: a `.mjs` file that runs in its own process, watches events
(a task changed, a message arrived…) and can add context to your turns.

```json
"plugin": { "entry": "plugin.mjs", "observe": ["task.updated"], "context": false, "network": false }
```

It runs sandboxed with Node's permission model: it reads only its folder, writes only its data folder, starts no
processes and can't call APX. It reaches the internet only with `"network": true`, and never this machine. What it
adds as context reaches the agent as outside data, not as instructions.

<Aside type="caution">
An extension with a plugin runs code on your computer. The panel says so before you turn it on: do it only if you
trust its author.
</Aside>

<Aside type="tip">
APX ships an `apx-extensions` skill for Claude Code, Codex and other agent apps, so you can ask one of them to build
an extension for you. See [Skills](/extend/skills/#teach-other-agent-apps-to-use-apx).
</Aside>
