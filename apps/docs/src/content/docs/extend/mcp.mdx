MCP (Model Context Protocol) servers add tools: a GitHub server lets agents read issues, a database server lets them
query, and so on. APX runs the servers your agents use and keeps each tool behind your permissions.

<Aside type="note">
This page is about servers **APX's agents** use (`apx mcps`). To use APX **from** Claude Code, Codex or another MCP
client, see [Outside clients](/extend/outside-clients/).
</Aside>

## Global and project servers

- **Global** servers are yours. Every project inherits them; a project can turn one off for itself, or stop using
  the global ones altogether. Their environment and headers may use your [variables](/extend/integrations/#variables-and-secrets)
  as `secret://NAME`.
- **Project** servers are declared in the project's `.apx/mcps.json`, committed with the repository:

```json title=".apx/mcps.json"
{
  "mcpServers": {
    "docs": { "command": "npx", "args": ["-y", "@acme/docs-mcp"] },
    "status": { "url": "https://mcp.example.com/status" }
  }
}
```

A repository can name any command, so **a project server starts only after you approve that exact definition**. If
the file changes, it needs approving again. `.apx/mcps.json` never holds tokens: a definition that mentions
`secret://` is ignored there.

### Private servers for one project (development preview)

An owner's server can be limited to one project while its configuration stays private in APX, not in the repository.
It can use that project's variables. Approvals for the same configuration and credential scope are kept; a different
project account asks for permission again:

```bash
apx mcps scope github acme-store           # only this project
apx mcps scope github global               # available everywhere again
```

In the connection editor, **Lives in** offers **Global** or a project by name: a server that lives in a project is
listed among that project's own, and only its agents use it. For a global server, **Available in** picks the projects
it is on in (**All projects**, or some of them); the same switches show under **By project** in its detail, and the
list says **In 2 of 3** instead of **Global** while it is off somewhere. Save applies both; Cancel leaves them
unchanged. Repository connections keep belonging to their repository and do not offer these controls.

To stop a server everywhere without removing it, turn off **On** in its detail, or pick **Turn off** in its right-click
menu. Its definition and approval stay, and the same switch turns it back on, also when an agent turned it off for
you. A server that is off is not tested and its tools are not offered to agents.

Before making it global, check that its variables exist in the places where you will use it. Project variables are
not copied into the global store. The editor names any variables that need a value in the selected scope; you can
still save a connection while preparing those values. This does not move a repository's `.apx/mcps.json` definition.

### Variables and links from chat (development preview)

**Use a variable** beside an environment or header value opens a searchable list. You can also press **Ctrl+Space**
inside the value, use the arrow keys and press Enter. Picking a name inserts a chip at the cursor, preserving text
such as `Bearer `; you can keep typing after the chip, or before it. The list uses the selected project's effective variables: its own value wins over its parent's
or the global value, and each name appears once. **New variable…** stores a value in that same scope before inserting
its reference. No values appear in the picker.

A link such as `[Acme](apx:resources/mcp/acme/global)` opens a private connection's editor over the chat, even when it
is limited to a project. For a repository connection use `apx:resources/mcp/acme/PROJECT_ID`. Without the last segment,
a duplicate name asks which connection you mean. A missing exact target never opens a different connection with the
same name. Closing or saving returns to the same conversation.

## Add, approve, remove

<Tabs>
<TabItem label="Panel">

In **Resources › MCP**, **+ MCP** opens **New MCP server**: a name, **How it connects** (**Command** or **URL**), and
its **Environment** or **Headers**, where a value can be one of your variables. A project's server shows **Approve**
until you approve it; read the command first. **Test** starts it and lists its tools.

A server someone gave you as a link can also be added in the **Marketplace**, with **Add › From an address**: it
becomes one of your extensions (**Yours**), listed and connected there, not here. A server you write in
**Resources › MCP** stays a plain server and is not listed in the Marketplace
([Extensions](/extend/extensions/)).

</TabItem>
<TabItem label="Terminal">

```bash
apx mcps                                   # every server: status, tool count, error or target
apx mcps list acme-store                   # as one project sees them
apx mcps add github -- npx -y @modelcontextprotocol/server-github
apx mcps add status https://mcp.example.com/status
apx mcps trust acme-store docs             # approve a project's server as its file defines it now
apx mcps untrust acme-store docs
apx mcps rm github
```

Put `--` before a command whose arguments start with `-` (like `npx -y`), so `apx` doesn't read them as its own
options. Environment and headers are edited in the panel.

</TabItem>
</Tabs>

Servers don't run all the time: a server is **Ready** and starts only when an agent first uses it.

A server that signs in through your browser (one run with `mcp-remote`, for example) opens its sign-in page the
first time it starts. If you don't finish, it shows **Needs you to sign in** and APX doesn't start it again by
itself, so your browser doesn't keep opening. Click **Sign in** on the server (or run `apx mcp signin <server>`) when
you are ready, and finish on the page it opens.

While it waits, the server shows **Open the sign-in page**, and **Sign in** becomes **Start over**: use it only if
you want a new page, since the one you opened stops working. You have five minutes to finish.

### APX on another computer

When APX runs on a server or another computer, the sign-in page returns to a `localhost` address on that computer,
so your browser ends on a page that does not load (`http://localhost:44776/oauth/callback?code=…`). That is
expected. Copy that whole address, paste it in the field under the link and click **Finish**: APX opens it on its
own computer and the server starts. Only the address of the sign-in in progress is taken, with its own code and
state. Services such as Tiendanube only accept a `localhost` return address, so this works where pointing the
return at the server's IP is refused.

## Try a server from the terminal

`apx mcp tools`, `run` and `check` talk to a server directly, which is handy when something doesn't work:

<Terminal command="apx mcp check github">{`github: OK · 812 ms · 26 tools`}</Terminal>

```bash
apx mcp tools github                       # every tool with its schema and a ready-made run command
apx mcp tools github search_issues         # just one
apx mcp run github search_issues '{"q":"repo:acme/store is:open label:bug"}'
echo '{"q":"is:open"}' | apx mcp run github search_issues -
```

Add `--project <id>` for a project's server, and `--scope global|project` when a name exists in both.

### A server redirects to another site (development preview)

For a URL connection, APX follows redirects within the same origin (scheme, host and port). It also permits an
HTTP-to-HTTPS upgrade on the same hostname when both use their default ports. Requests with a body only follow
307 or 308 redirects, which preserve the request method. Other redirects fail instead of forwarding your
variables or the request contents. If the service has moved, edit the connection to use its final URL after
checking that you trust the new address, then try **Test** again.

Connection and transport errors omit web addresses, so a server cannot expose a credential by encoding it in
a redirect address. Outside web addresses, masking covers the stored variables used by that connection as
literal values, usual JSON escaping and a single layer of percent encoding. This does not make an approved
third-party server safe: it still receives the credentials and data you choose to send it, and may transform
or return them in ways that masking does not recognize.

If you suspect an older connection redirected credentials to a site you do not trust, revoke or rotate those
credentials at the service and update their values in APX.

## Tool permissions

Each server has **Tool permissions**:

- **Ask first**: each agent asks you before using a tool that changes something.
- **All allowed**: no agent asks for its tools, ones the server adds later included. If a project's file changes, it
  waits for your approval again and keeps **All allowed** once you approve it.
- **Some**: click a tool to allow it (green) or to make it ask again. Tools the server adds later ask first, even when
  you had picked every tool; leaving one tool out of **All allowed** turns it into **Some**.

A connection you add starts on **All allowed**: you choose which tools ask first. Until you pick **All allowed**
yourself, its tools still ask while a web page, someone's message or another agent's answer is in the chat, so outside
text cannot make an agent act through it in your name. That holds for one you add here or
with `apx mcps add`, one an extension brings when you turn it on, a project's `.apx/mcps.json` once you approve it,
and an account you connect. Approving a project's file is still up to you. Connections you already had keep their
permissions, and changing a connection that was on **All allowed** (its command, an extension's settings) keeps it so.

You can also ask your super-agent in the chat: "review my MCP tools", "allow all of them", or "allow everything but
the ones that delete". It lists each connection's tools and changes them when you ask.

The list shows each server's tools and permissions as they were the last time it ran, so you see them without
opening it. Hover a server's dot for what it means: filled, running now; ring, ready (it starts when an agent uses
it); amber, it needs you (approve it or sign in); red, it did not start. Click one of its variables to open it in
**Variables**.

On top of that, an agent's own autonomy and its rules by case still apply (its `tools:` list says what it uses first,
not what it may reach), and anything you approved "always" for one
agent or chat shows under **Allowed for one agent or chat**. See [Autonomy](/concepts/autonomy/).

## Why agents see only two MCP tools

Sending every MCP tool to the model on every call gets expensive fast. On a real install, ten ordinary servers
brought 319 tools: a one-line answer cost **64,432 tokens** of prompt.

So agents don't get those tools directly. While any server is on and approved, they get two:

- `tool_search` loads tools by their exact names (several at once), or finds them by words or by server, with their
  descriptions and arguments.
- `tool_run` runs one by its exact name, for a model that will not call a tool it was not sent.

The same one-line answer then costs **11,838 tokens**, and the list of tools stays the same from call to call, which
keeps the model provider's prompt cache warm. Approvals, confirmations and the tool cards in the chat work exactly as
if the agent had called the tool directly.

APX's own tools that agents rarely need (routines, settings, Flows, widgets, documents, the computer's screen, contact
requests, images, video transcripts and a few more) travel the same way: `tool_search` names them grouped by what they are for, and
the agent calls one by its name whenever it needs it, with nothing to search first. If it gets the arguments wrong, the answer brings
them, so the next try works. This keeps a default call about a third lighter.

## Files and images in MCP tools

An agent can hand one of its files to an MCP tool: an image it drew, something you attached in the chat, or a file in
the folders it works in. In the tool's arguments it writes the file's media id (`med_…`) or `apx-file:<path>`, and
APX sends the file the way that field takes it:

- To a server that runs **elsewhere** (an `http(s)` URL), the field gets the file's contents in base64, within what the
  field says it accepts ("images under 8 MB") and never more than 20 MB. The file's type and name fill the tool's
  `mime_type` and `file_name` fields when it has them and the agent left them empty.
- To a server that runs **on this computer** (a command), a path field gets a real path. A drawing or an attachment is
  first copied into the chat's temp folder, so the server never reads APX's own folder.
- A field that only takes a public link, or a path a remote server would read on its own disk, is refused with the
  field to use instead. APX does not publish your files to get a link: for a large video, the service needs its own
  way to receive it (an upload link it hands out, then `curl` from the agent's temp folder).

The step keeps the reference, never the file's contents. Sending a file out waits for your OK while the turn has
outside content in it, even through a tool that says it only reads.

An agent can also copy a drawing or an attachment into a file of its own (`file_write` with `media`), for its shell,
its skills or another tool.
