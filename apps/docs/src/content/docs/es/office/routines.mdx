Una rutina es trabajo que un agente hace solo, con horario: revisar el stock cada mañana de semana, mirar los pull
requests abiertos cada hora, armar un resumen semanal para un cliente. Te enterás solo cuando hay algo para contarte.

Las rutinas viven en la pestaña **Rutinas** de cada proyecto (las de Home, en el proyecto base). **Nueva rutina**
abre el editor.

<Shot name="routines" alt="La pestaña Rutinas de un proyecto: cada rutina con su flujo, una fila de 14 barras de activación y su próxima corrida" caption="Rutinas, con sus últimas activaciones" />

## Acciones

Cada rutina hace una de cuatro cosas:

| Acción | Qué pasa |
|---|---|
| **Agente** | Un agente (Home o uno del proyecto) responde tu prompt. Te avisa solo cuando tiene algo para decir. |
| **Mensaje** | Te manda un mensaje fijo por tu canal (Telegram, WhatsApp…). Sin modelo. |
| **Shell** | Solo corre un comando en la carpeta del proyecto. Sin modelo ni aviso. |
| **Vigía** | Recorre tu trabajo buscando lo que vale una palabra (tareas atrasadas, compromisos por vencer, proyectos quietos, tareas armadas de forma que no pueden avanzar) y llama al modelo solo cuando hay algo nuevo. |

**Novedades del equipo** es una [capacidad de secretaría](/es/office/secretary/), que activás o desactivás desde **Configuración → Super-agente**, no una acción de rutina. Lo que una integración hace sola, como la revisión de mails nuevos de Gmail o los recordatorios de eventos de Google Calendar, tampoco es una rutina: se prende y se ajusta en la configuración de esa integración.

## Horarios

| Cuándo | Ejemplo |
|---|---|
| **Con horario** | Elegí días y hora ("Días hábiles a las 08:30"), o **Escribir un cron**: cinco campos, en tu hora local. `30 8 * * 1-5` es días hábiles a las 08:30. |
| **Cada** | Cada N minutos, horas, días o semanas. Mínimo 5 minutos. |
| **Una vez** | Una sola fecha y hora. |
| **A mano** | Solo cuando apretás **Correr ahora**. |

Una corrida que se perdió con el core apagado corre una vez cuando vuelve, nunca dos.

## Flows

En la rama de integración todavía no publicada, abrí **Flows** en el sidebar global junto a **Tareas** y **Recursos**.
La lista muestra todos los flows de todos los proyectos con sus pasos, cuántos usan IA, una barra por cada una de sus
últimas rondas y un interruptor de encendido; el menú de proyecto la acota. El acceso de Rutinas abre esta misma
pantalla global. Los enlaces directos usan `#view=flows`, `#view=flows&scope=<project-id>`,
`#view=flows&flow=<flow-id>` (sus rondas) o `#view=flows&flow=<flow-id>&edit=1` (su editor); los botones del chat
pueden usar `apx:flows`, `apx:flows/<project-id>`, `apx:flows/<project-id>/<flow-id>` o
`apx:flows/<project-id>/<flow-id>/edit`.

**Nuevo flow** abre el editor, en blanco o desde una forma de arranque. Sumá pasos desde la izquierda (se unen después
del paso elegido), arrastrá desde el punto de salida de un paso para unir dos pasos y configurá cada uno a la derecha:

| Paso | Qué hace |
|---|---|
| Webhook entrante | Arranca el flow cuando un servicio manda un POST. Su URL aparece al guardar. |
| Horario | Arranca el flow a horas fijas: **Cada 5 min**, **Cada hora**, **Hábiles 08:30**, **Diario 03:00** o una expresión cron (minuto, hora, día, mes, día de la semana), en tu zona horaria. El panel lateral muestra las próximas rondas. |
| Condición | Prueba sus casos en orden y sigue por el primero que se cumple; si no, por su última salida. Un caso es un campo de lo que llegó que *es* un valor (`form.tier` es `A`) o una **fórmula** (`$trigger.amount > 100 && $vars.vip`). Con un caso se lee **Sí** y **No**; con más, cada caso tiene su punto, con su nombre, y además **Si no**. Sin modelo. |
| Variables | Nombra valores una vez para los pasos que siguen: texto, un número, sí o no, o una fórmula sobre `$trigger`, `$steps` y las variables de arriba. Los pasos siguientes los leen como `$vars.nombre`. Un valor puede guardar una clave elegida de tu lista (`secret://nombre`): se usa solo en los headers de un webhook saliente y en las variables de un comando, y un flow que la pone en un mensaje, un cuerpo o una instrucción no se puede guardar para que corra. Sin modelo. |
| JavaScript | El cuerpo de una función corta que recibe `input` (lo que llegó o el resultado de un paso anterior) y `vars`, y devuelve lo que los pasos siguientes leen como `$steps.<paso>`. Corre aparte, con tiempo máximo, y no puede abrir archivos, usar internet ni correr programas. Sin modelo. |
| Leer tabla | Elige una de las tablas del proyecto (muestra cuántas filas tiene cada una) y lee una clave, como `$trigger.email`, o sus últimas filas. Los pasos siguientes leen `$steps.<paso>.row` o `.rows`. Un Leer tabla después de un Guardar en la tabla ofrece primero la tabla de ese paso. Sin modelo. |
| Guardar en la tabla | Elige una de las tablas del proyecto, o una nueva que nombrás ahí (se crea con su primera fila), y guarda lo que llegó, un campo o el resultado de un paso anterior con una clave. La clave puede salir de lo que llegó (`$trigger.email`); guardar otra vez con la misma clave reemplaza esa fila. Sin modelo. |
| SQL | Una instrucción sobre un archivo SQLite en la carpeta del proyecto (`data/app.db`). Los valores van aparte de la consulta, como `:nombre` con una línea `nombre: $trigger.email`, nunca adentro. **Solo lectura** lee filas (`$steps.<paso>.rows`, hasta 500); apagado, puede agregar, cambiar y borrar filas y agregar tablas o índices. Sin modelo. |
| Modelo IA | Le da una tarea a un agente del crew o a un bot de este flow, con lo que llegó o el resultado de un paso anterior, en el harness y el modelo que elijas (ver abajo). Gasta tokens. |
| Rutina | Corre una rutina manual del proyecto. |
| Modelo directo | Le pregunta una vez a un modelo configurado, sin herramientas, y pasa su respuesta. Gasta tokens. Queda en los flows que ya lo tienen; los pasos nuevos usan **Modelo IA**. |
| Webhook saliente | Llama a una URL con GET, POST o PUT. Headers y body pueden llevar valores de la ronda; una clave va en un header como `secret://nombre`, de **Secretos**. Los pasos siguientes leen su respuesta como `$steps.<paso>.status`, `.ok` y `.json` (o `.body` si no es JSON). |
| Cmd | Un comando de shell en la carpeta del proyecto, como el de una rutina. Los valores de la ronda le llegan solo como variables (`EMAIL=$trigger.email`, que lee como `$EMAIL`) y como su entrada, nunca dentro del texto; una clave va en una variable como `secret://nombre`. Los pasos siguientes leen `$steps.<paso>.stdout` y `.exit`; un error corta el flow salvo que **Seguir si falla** esté prendido. Tiene tiempo máximo (hasta 2 minutos). |
| Avisar | Manda un mensaje como vos por una de tus apps de chat (Telegram, WhatsApp, Discord…) a alguien que conocés ahí, a vos o a una sala que listaste. Con **Solo si hay algo para contar**, no manda nada cuando todos los valores del mensaje salen vacíos. |

La barra de arriba del editor tiene el nombre del flow a la izquierda y **Salir** a la derecha, junto al estado de
guardado, **Probar ronda** y **Guardar**; si hay cambios sin guardar, pregunta antes de salir.

### Quién responde en un paso Modelo IA

Un flow es de un proyecto, que se elige arriba al crear el flow: los pasos que lo necesitan (agentes, tablas, rutinas,
una carpeta) lo dicen hasta que lo elegís. Los campos de texto ofrecen valores mientras escribís `$`, `{{` o
`secret://`, o con su botón de llaves; donde puede ir una clave, la lista también ofrece **Guardar una clave**.

**Quién responde** es **Un agente** (uno del crew, con sus instrucciones, personalidad, memoria y herramientas) o **Un
bot de este flow**: un nombre y **Cómo trabaja**, el prompt de sistema que escribís. Un bot arranca de cero en cada
ronda: sin memoria, sin historial y sin equipo, y trabaja solo con la web, los archivos y comandos del proyecto y su
propio navegador, nunca con tus chats, correo, calendario o cuentas. Después elegí:

- **Agente del crew**: los agentes del proyecto y, siempre, tu super-agente, como tarjetas.
- **Harness**: **APX** (el propio de APX, sobre las APIs de modelos que configuraste) o una app de esta computadora como
  Claude Code o Codex, si está instalada. En una app, el paso corre en la carpeta del proyecto con las herramientas y la
  configuración de esa app, en una sesión propia; quién responde va en su encargo, y la memoria de APX no le llega.
- **Modelo** y, si el modelo lo acepta, **Esfuerzo**. Si lo dejás como está, un agente usa su propio modelo y un bot tu
  modelo por defecto.
- **Permisos**: en APX, los del agente, **Pregunta antes**, **Auto** o **Total**; en una app, **Pregunta antes**,
  **Edita libre** o **Solo lectura**. Un flow corre sin nadie mirando: lo que pregunta te espera hasta el tiempo máximo
  de la ronda.
- **Puede pedirle a otros agentes** (solo agentes en APX), apagado de entrada. Apagado, el agente trabaja solo con todas
  sus herramientas y su memoria, pero no puede pasarle trabajo a tus otros agentes, escribirles, ni crearles o
  comentarles tareas. Prendido, trabaja como en un chat.

La ronda muestra quién respondió, en qué harness y modelo, y **Abrir chat** abre la conversación que tuvo.

Un flow tiene un solo disparador. Un flow corre como está dibujado: los pasos pueden abrirse en caminos y volver a
juntarse, y cada paso puede recibir lo que llegó o el resultado de un paso anterior. En **Sigue con** elegís por cuál
salida de una condición sale cada conexión; un paso que sumás después de una condición toma su primera salida libre. El panel dice *Corre así como está* o por qué todavía no puede correr (un agente fuera del proyecto, un modelo
sin configurar, dos pasos que guardan en la misma clave sin orden entre ellos, un horario más seguido que cada 5
minutos), también en un flow nuevo antes de guardarlo por primera vez.

**Guardar** conserva tu dibujo. Si el flow está prendido, guardar también lo convierte en lo que corre: los eventos
nuevos lo usan y los que ya llegaron terminan con la versión con la que empezaron. Si está apagado, prenderlo convierte
tu último dibujo guardado en lo que corre. Un flow con la forma vieja de un solo camino (webhook, condiciones, leer,
guardar y un agente o rutina) sigue corriendo como antes hasta que guardes un dibujo que esa forma no puede representar.
**Probar ronda** sigue datos de ejemplo por las condiciones y los caminos y marca los pasos a los que llegaría, sin
guardar, leer la tabla, mandar ni pasarle nada a un agente; un paso que necesita la respuesta de otro dice que depende
de ella.
Guardar nunca corre nada, y un flow nuevo arranca apagado.

Al abrir un flow ves sus pasos como corrieron en la ronda elegida (numerados, en verde si corrieron, punteados si no,
en rojo si fallaron), qué recibió y qué dio cada paso, cuándo empezó y terminó, un log y las rondas a la derecha con su
duración y tokens. Una ronda hecha con un dibujo anterior muestra ese dibujo y dice **Versión anterior**. Una ronda que
cortó una condición marca esa condición con **no** y los pasos siguientes como no corridos. Un paso que le pasó trabajo
a un agente abre su chat.

Cada ronda tiene 10 minutos desde que llega su evento; un paso de modelo tiene su propio límite (hasta 2 minutos). Los
pasos que llaman a un modelo se mandan una vez y nunca más: si APX se detiene o la respuesta no llega a tiempo después
de mandar el pedido, la ronda dice **Para revisar** en lugar de reintentar, porque el modelo pudo haberlo hecho igual. Los
comandos y las escrituras SQL siguen la misma regla: uno cortado por un reinicio, el tiempo máximo o **Detener ronda**
no se vuelve a correr. Prender un flow con un comando o una escritura SQL pregunta antes (**¿Dejás que este flow actúe
por vos?**), con el comando y la carpeta o la base; cambiar cualquiera de los dos vuelve a preguntar.
Apagar un flow frena los pasos nuevos; una ronda que estaba esperando termina igual al llegar su límite. Un flow corre
un evento por vez, en el orden en que llegaron.

**Correr ahora**, en la página del flow, lo arranca en el momento por el mismo camino que su disparador. Un flow con
horario corre con un evento vacío; uno con webhook te pide el cuerpo que recibe, cargado con el último que llegó, y lo
trata como cualquier dato de afuera. La ronda dice **La arrancaste vos**. **Detener ronda**, en una ronda que está
corriendo, la frena: los pasos que no empezaron no corren y un paso que ya se le mandó a un modelo queda **Para
revisar**, sin volver a mandarse.

Un flow con horario corre mientras APX está prendido. Si APX estaba apagado a la hora de una ronda, el flow corre una
vez al arrancar APX (no una por cada hora que se perdió) y esa ronda dice que arrancó tarde. Si la ronda anterior sigue
corriendo cuando llega la hora siguiente, esa hora se salta, no se encola, y la página del flow dice cuántas se saltaron.
Un flow apagado no corre por horario y, al prenderlo de nuevo, cuenta desde ese momento. Un flow con horario no tiene
dirección: nunca recibe un POST, y uno con webhook nunca corre por horario.

### Mensajes y llamadas que un flow hace por vos

El texto de un paso lleva valores de la ronda: `$trigger.email` es un campo de lo que llegó, `$steps.<paso>.text` la
respuesta de un paso anterior, `$vars.nombre` una variable, `$apx.project`, `$apx.now` y `$apx.run` el nombre del
proyecto, la fecha y hora y el número de ronda, y `$$` es un signo de pesos. No hace falta saberlos: en cualquier campo
que acepta valores, escribí `{{` o `$`, o tocá el botón **{}**, y elegí entre lo que llegó, los pasos anteriores, las
variables del flow y los valores de APX; lo que elegiste se ve como una insignia. Los **Secretos** se ofrecen solo en los
headers de un webhook saliente y en las variables de un comando, donde el paso los lee por su cuenta; un mensaje, un
body o una instrucción de IA nunca reciben uno. Lo que
llega solo llena las palabras: quién recibe el mensaje es la persona o sala que elegiste, nunca una que nombren los datos.

Como Avisar habla como vos y un webhook saliente actúa sobre otro servicio, la primera vez que un dibujo mandaría o
llamaría a un lugar nuevo, guardarlo prendido (o prenderlo) pregunta **¿Dejás que este flow actúe por vos?** y lista
cada persona, sala y dirección. **Permitir** lo convierte en lo que corre; **Ahora no** deja corriendo la versión
anterior. Después, cada ronda manda sin volver a preguntar.

Cada mensaje y cada llamada que cambia algo sale una sola vez: si APX se detiene o el otro lado no responde después de
mandarlo, el paso dice **Para revisar** en lugar de repetirlo (revisá el chat o el servicio). Un GET, que no cambia
nada, prueba una vez más si la conexión falla antes de cualquier respuesta. Un flow manda como mucho 20 mensajes por
hora y hace como mucho 60 llamadas que cambian algo; la siguiente falla sin salir. Un mensaje a una app de chat que no
está andando se retira, no sale después. Un webhook saliente solo llama a direcciones de internet: una dirección de esta
computadora o de una red privada se rechaza, también cuando un nombre apunta ahí, y no sigue redirecciones. De la
respuesta se leen hasta 256 KB (16 KB de texto), los archivos solo se mencionan, y un secreto que usó nunca aparece en
la ronda, solo `secret://nombre`.

### Pedile un flow a tu super-agente

Pedilo en cualquier chat ("cuando llegue un lead de la web, guardalo y avisame por Telegram") y tu super-agente dibuja el
flow en el proyecto que corresponde, o cambia los pasos de uno que ya tenés. Ubica los pasos, revisa qué impide que
corra y lo arregla. El chat muestra el dibujo del flow, si es un borrador, y **Abrir en el editor**.

Lo que guarda es un borrador: nada corre hasta que lo revisás en el editor y prendés el flow (o lo guardás estando
prendido). Prender un flow cuyos últimos cambios dibujó un agente abre primero su editor: revisalos y tocá **Guardar**
para hacerlos tuyos. Los mensajes, llamadas, comandos y escrituras en bases de datos te preguntan **¿Dejar que este flow actúe por
vos?** antes. Si en el chat había un mensaje de otra persona o una página web, el super-agente te pregunta antes de
guardar el borrador. Qué tan libre actúa un paso Modelo IA (su modo de permisos, si puede pedirle a otros agentes) lo
elegís vos en el editor. La lista y la página de un flow muestran los
cambios del agente apenas se guardan; un editor abierto conserva lo que tiene en pantalla, así que salí y volvé a abrirlo
para verlos (si guardás encima, te avisa que el flow cambió).

El CLI también arranca y detiene rondas: `apx flows run <flow> ['<cuerpo de ejemplo JSON>']` y
`apx flows stop <flow> <evento>`. Actúan como vos, así que no corren dentro del comando de un agente.

Un Flow pertenece a un proyecto. Encendé un flow con webhook antes de crear su token en
**Configuración → Dispositivos → Endpoints**. El acceso público se configura por separado y nunca expone el RPC privado
ni el panel.

Enviá JSON como `{"id":"order-42","data":{"status":"paid"}}` a `POST /flows/<id>` con el token bearer de esa ruta.
Conservá el mismo ID de evento en los reintentos. Los eventos vacíos, duplicados o que no coinciden con los filtros no
llaman al modelo; el trabajo coincidente usa el vínculo guardado, no una identidad ni un comando elegido por el payload.
Las tablas y el historial persisten tras reiniciar. Una ejecución vinculada puede fallar y no se garantiza exactamente
un efecto en servicios externos. El panel muestra las últimas 50 rondas (**Ver rondas anteriores** trae más) y hasta 20
filas de la tabla; los métodos privados del protocolo
`flows.rows` y `flows.events` permiten inspeccionarlos con paginación.

Rotar invalida el token anterior inmediatamente. Si falla el borrado de su secreto, queda una referencia que no autoriza
pedidos, para reintentar la limpieza al iniciar el core o en la próxima rotación; la credencial nueva se devuelve igual.
La creación interrumpida de un token también queda registrada para limpieza. Si la cola de limpieza se llena (1.000
referencias), recuperá el backend de Secrets antes de rotar. Usá la misma clave de idempotencia al reintentar un pedido
de administración cuya respuesta se perdió.

## El silencio también es una respuesta: SKIP

El prompt de una rutina de agente son tus propias palabras. Cuando esta vez no hay nada que valga contarte, el agente
responde solo `SKIP` y no te llega nada. Escribí prompts que dejen lugar para eso:

> Revisá los pedidos de ayer buscando algo raro: reembolsos de más de 200, un producto vendiendo 3 veces su promedio,
> un pago rechazado. Si no hay nada, respondé SKIP.

## Comandos antes y después

**Agregar comandos antes y después** le suma a la rutina un pre-comando y un post-comando. Los dos son comandos de
shell que escribís vos (los agentes no pueden), corren en la carpeta del proyecto, dos minutos como máximo y sin
credenciales en su entorno.

<Steps>

1. **Pre-comando** corre primero. Su salida le llega al agente donde escribas `{{pre_output}}` en el prompt (o
   después del prompt si no lo ponés), marcada como dato de afuera.
2. **Llamar al modelo** decide si el agente corre, según el resultado del pre-comando:

   | Opción | Se llama al modelo |
   |---|---|
   | **Siempre** | cada vez |
   | **Si hay salida** | solo cuando el pre-comando imprimió algo |
   | **Si falla** | solo cuando el pre-comando salió con error |
   | **Nunca** | nunca (corren solo los comandos) |

3. **Post-comando** corre al final con lo que salió, en estas variables de entorno:

   | Variable | Valor |
   |---|---|
   | `APX_LLM_OUTPUT` | Lo que respondió el agente (o el mensaje) |
   | `APX_STATUS` | `completed`, `failed` o `skipped` |
   | `APX_SKIPPED` | `1` si no se llamó al modelo, si no `0` |
   | `APX_PRE_OUTPUT` | La salida del pre-comando |
   | `APX_PRE_EXIT` | El código de salida del pre-comando |

</Steps>

Así una rutina gasta **0 tokens** los días tranquilos: el pre-comando de Tomás lista los productos con poco stock,
con **Si hay salida**, y el modelo se llama solo los días en que hay alguno.

Una rutina de **Mensaje** también usa `{{pre_output}}`: "El clima de hoy: `{{pre_output}}`" te manda la salida del
comando tal cual, sin modelo.

## Anclas: llega siempre

Las novedades de una rutina normalmente pasan por tu [presupuesto de interrupciones](/es/office/secretary/#el-presupuesto-de-interrupciones):
un tope diario, espacios entre avisos, horario de silencio. Prendé **Llega siempre** en una rutina que nunca querés
que se frene, como un resumen de la mañana: sus novedades llegan aunque sea de noche o ya se haya llegado al tope, y
no cuentan para él.

## Correr ahora y las barras de activación

**Correr ahora** arranca una rutina en el momento, tenga el horario que tenga. Cada rutina muestra sus **últimas
activaciones** como 14 barras, de la más vieja a la más nueva:

| Barra | Significa |
|---|---|
| **La acción corrió** | Corrió y no tenía nada para contarte. |
| **Te avisó** | Corrió y te mandó algo. |
| **Salteada, 0 tokens** | No se llamó al modelo (el pre-comando no lo pidió, o no había nada nuevo para vigilar). |
| **Falló** | La corrida falló. |
| **No corrió** | Un momento en que tenía que correr y no corrió. |

Cada corrida es un chat propio, así que podés abrirla y ver exactamente qué hizo el agente.

## Desde la terminal

<Terminal command="apx routines help">{`apx routines                                   Routines and when they run next
apx routines add <name> <prompt…> --agent a [--project p] (--cron "30 8 * * 1-5" | --every 60 | --at <ISO date>)
                 [--pre "<command>"] [--call always|output|fails|never] [--post "<command>"]
                                                The pre-command's output reaches the prompt at {{pre_output}}
apx routines run <id>                          Run now
apx routines on|off <id>
apx routines rm <id>
apx routines log <id>                          Recent runs`}</Terminal>

Sin `--cron`, `--every` ni `--at`, la rutina corre a mano. `--every` va en minutos. La CLI crea rutinas de agente;
las de mensaje, shell y vigía, y las anclas, se configuran en el panel.

```bash
# Días hábiles a las 9: Tomás mira el stock bajo, solo cuando hay
apx routines add stock-bajo "Esta es la lista de stock bajo de hoy: {{pre_output}} Armá el pedido para el proveedor." \
  --agent <id-tomas> --project <id-acme> --cron "0 9 * * 1-5" \
  --pre "./scripts/low-stock.sh" --call output

apx routines run <id-rutina>     # probala ahora
apx routines log <id-rutina>     # corridas recientes; "(nothing to say)" marca un SKIP
```

<Aside type="note">
Las rutinas son tuyas: solo vos las creás o las cambiás. Un agente no puede programarse trabajo fijo a sí mismo.
</Aside>
