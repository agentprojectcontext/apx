Casi todos los problemas se reducen a tres preguntas: ¿el core está corriendo?, ¿este cliente llega a él?, ¿lo deja
entrar? Empezá por ahí.

## ¿El core está corriendo, y con qué código?

`apx status` le pregunta al core mismo. La primera línea es la versión y el commit que corre (`code_sha`), y después
vienen cuánto lleva prendido, la memoria, la URL y el estado de cada subsistema:

```bash
apx status          # versión y code_sha del core, subsistemas, equipo, dispositivos, acceso
apx --version       # la versión y el commit de esta CLI, sin preguntarle al core
apx service status  # ¿el servicio está instalado, y el core responde?
```

Si el commit no es el que esperás (por ejemplo, después de actualizar), el core sigue corriendo el código viejo:
reinicialo con `apx service restart`, o cerrá y abrí la app de escritorio. En el panel, **Configuración › Avanzado**
muestra la misma versión y el `code_sha`.

Si el core no está corriendo, vas a ver:

<Terminal command="apx status">{`apx: Core not running: See why and what to do: apx doctor`}</Terminal>

`apx doctor` revisa esta computadora sin el core: qué dice el log del core sobre su último arranque, si el servicio
está instalado y corriendo, y si salió un APX más nuevo. Termina con el comando a correr. Si una versión no puede
arrancar (su log muestra `ERR_MODULE_NOT_FOUND`), `apx update` la reemplaza aunque el core esté caído, en un APX
instalado con el script de instalación; la app de escritorio se reemplaza bajando la más nueva.

Si no, arrancalo con la app de escritorio, con `apx service install` (o `apx service restart` si el servicio ya
existe), o con `pnpm dev` desde el código. Si arranca y se cae, leé su log.

### Una migración impide arrancar

Ejecutá `apx doctor --fix` (o `apx doctor fix`) en el servidor afectado con su `APX_HOME`, sin `APX_URL`.
Con el core caído puede reconciliar el esquema hotfix 109 exacto y reconocido con el esquema integrado 115.
Rechaza un daemon activo, otras conexiones a la base y objetos de esquema desconocidos. Nunca elimina un índice
desconocido ni reinicia la versión. El backup SQLite privado en `<APX_HOME>/backups/` incluye datos confirmados en WAL.
La reparación es transaccional y valida integridad y claves foráneas antes de confirmar; un fallo conserva el estado
original e informa el backup si llegó a crearlo. No sobrescribas la base ni borres sus archivos WAL por tu cuenta.
Después de un éxito, arrancá APX normalmente y ejecutá `apx doctor` para comprobarlo; la reparación no reinicia servicios.
Si no reconoce el esquema, conservá los datos y compartí el diagnóstico y las definiciones del esquema con soporte.
Con el core activo, `--fix` mantiene la compactación del historial en lugar de reparar migraciones offline.

## Dónde están los logs

Corra como corra APX (la app de escritorio, el servicio o `pnpm dev`), el core escribe su log en el mismo archivo,
en la carpeta `logs` de su home. Una línea JSON por evento; las credenciales que aparezcan se reemplazan por
`[redacted]`.

| Sistema | El log del core |
|---|---|
| macOS | `~/.apx/v2/logs/core.log` (`/Users/<vos>/.apx/v2/logs/core.log`) |
| Linux | `~/.apx/v2/logs/core.log` (el servicio además lo manda a `journalctl --user -u apx -f`) |
| Windows | `%USERPROFILE%\.apx\v2\logs\core.log` |

Si definiste `APX_HOME`, es `<APX_HOME>/logs/core.log`. Cuando el archivo pasa los 20 MB, el core guarda el viejo
como `core.log.1` y empieza uno nuevo.

Tres formas de leerlo:

- En el panel: **Configuración › Registros** muestra las líneas más nuevas primero, con filtro por nivel, búsqueda y
  la ruta del archivo para copiar.
- `apx logs` le pregunta al core (sirve también para un core en un servidor), con `-n 200`, `--level error`,
  `--grep texto` o `--json`. Si ningún core responde, lee el archivo de esta computadora.
- `apx service logs -f` lee el archivo de esta computadora y lo sigue.

<Terminal command="apx logs --level error -n 2">{`# ~/.apx/v2/logs/core.log
2026-10-15 09:12:03  ERROR  core  channel stopped  {"channel":"acme"}
2026-10-15 09:14:47  ERROR  output  TypeError: Cannot read properties of undefined`}</Terminal>

Las líneas del origen **Salida del proceso** son lo que el core imprimió fuera de su log, como la traza de una caída.

Las versiones de la app de escritorio anteriores a este cambio escribían `core.log` en la carpeta de logs de la app
(`~/Library/Logs/APX` en macOS, `%APPDATA%\APX\logs` en Windows, `~/.config/APX/logs` en Linux); las líneas
viejas siguen ahí.

## La base de datos de APX es grande o el panel está lento

Todo lo que guardan tus chats vive en un archivo, `apx.db` en la carpeta de APX. APX lo mantiene chico solo: cada
pocos minutos borra las copias de resultados de herramientas que tiene dos veces y, en los turnos que terminaron hace
más de dos semanas y tienen turnos más nuevos después, guarda una salida larga como el agente ya la lee en ese chat
(una nota corta de que se omitió). Lo que un chat le manda a su modelo no cambia. Una instalación nueva le devuelve
al disco el espacio liberado sola.

Una instalación anterior a este cambio tiene que reescribir el archivo una vez para devolver el espacio. Cuando el
archivo es grande, tu super-agente te avisa. Abrí **Configuración › Almacenamiento** y tocá **Compactar** en **Achicar
el archivo de chats**, o, con el core andando:

<Terminal command="apx doctor --fix">{`Compacting the database (a big one takes a few minutes; chats wait meanwhile)…
Database: 1110 MB → 890 MB (220 MB freed)
Old turns compacted: 2760, outputs kept twice removed: 66396
A copy from before was saved in APX's backups folder: apx-before-compact-20261106-123045.db
The database file was rewritten once; from now on it gives space back by itself.`}</Terminal>

Antes de cambiar nada, guarda una copia del archivo en **Copias de seguridad** (`backups/` en la carpeta de APX). La
copia queda hasta que la borres desde **Configuración › Almacenamiento › Copias de seguridad**. Mientras corre, los
chats y las rutinas esperan. Necesita lugar en el disco para esa copia más unas dos veces el tamaño del archivo para
reescribirlo; con menos, no cambia nada y lo dice: liberá espacio y corrélo de nuevo.

Cambia una cosa: si volvés a (o copiás un chat desde) un mensaje de hace más de dos semanas y unos turnos atrás, el
agente ve esos resultados viejos como la nota y vuelve a llamar a la herramienta si los necesita.

## El disco está casi lleno

Cuando al disco donde está la carpeta de APX le quedan menos de 5 GB libres, el panel lo avisa: una tarjeta al pie de
la barra lateral, o una franja debajo de la barra superior en el teléfono. **Ver almacenamiento** abre
**Configuración › Almacenamiento**, que muestra lo que APX guarda por área (chats, memoria y archivos; proyectos; las
computadoras de los agentes; el navegador; modelos locales; registros; caché; copias de seguridad).

**Liberar espacio** borra solo lo que APX vuelve a crear cuando lo necesita, y el botón dice antes cuánto es:

- las vistas previas de videos, y las copias de documentos abiertos en otra app (después de un día);
- los registros rotados, los demás registros sin cambios hace 14 días (nunca el actual) y la salida de comandos en
  segundo plano sin cambios hace 30 días.

Tus chats, memoria, archivos, proyectos, skills, secretos, copias de seguridad, las computadoras de los agentes, el
perfil del navegador y los modelos locales no se tocan con ese botón.

La app de APX en tu teléfono también lo avisa, arriba en **Más**, con un botón **Liberar espacio** que hace lo mismo y
dice cuánto liberó.

Si no alcanza, lo más grande suele ser las computadoras de los agentes y las copias de seguridad, y esas se borran de a
una:

- **Computadoras de los agentes** abre la lista de cada una, con su tamaño, si está encendida y cuándo se usó por
  última vez. Una computadora que dejó una prueba aparece como tal. **Borrar** pregunta antes: se pierde todo lo que
  tus agentes instalaron o guardaron adentro, y la computadora de tus agentes se vuelve a preparar desde cero la
  próxima vez que un agente la necesite. Una computadora encendida no se puede borrar: primero **Apagar** (se apaga
  para todos los agentes).
- **Copias de seguridad** abre la lista de cada copia de tus chats, memoria y tareas, por fecha y tamaño. **Borrar**
  pregunta antes y elimina esa copia para siempre; lo que APX tiene ahora queda como está.

Cuando cerrás la tarjeta (o la franja) del disco, queda un pequeño disco con un punto de aviso al pie de la barra
lateral, al lado del botón de ayuda, mientras el disco siga casi lleno; abre la misma pantalla, y se va solo cuando hay
lugar.

## Una actualización de la app no se instala

Si **Reiniciar ahora** no puede poner la versión nueva, la ventana de actualización dice por qué, o después de un
minuto avisa que APX no se reinició. Salí de APX (Cmd+Q en macOS, **Salir de APX** desde el ícono de la bandeja en los
demás) y volvé a abrirlo. En macOS y Linux, una versión ya descargada se instala cuando APX se cierra; en Windows,
elegí **Reiniciar ahora** otra vez cuando esté abierto. Si APX no se cierra, forzá la salida (Monitor de Actividad en
macOS, Administrador de tareas en Windows).

La app de escritorio anota cada paso de su propia actualización (descarga, reinicio, salida y, en macOS, el cambio de
`APX.app`) en `update.log`, dentro de su carpeta de logs: `~/Library/Logs/APX/update.log` en macOS,
`%APPDATA%\APX\logs\update.log` en Windows, `~/.config/APX/logs/update.log` en Linux. En macOS, si queda una carpeta
`.APX-<versión>.update` junto a `APX.app`, es una versión descargada que nunca se puso en su lugar; APX la borra la
próxima vez que arranca.

## macOS le pide a “node” acceso a Documentos

El core corre como `node`, la copia de Node que viene con APX. La primera vez que lee un proyecto en una carpeta que
macOS protege (Documentos, Escritorio, Descargas, iCloud Drive, un disco externo o de red), macOS pregunta si “node”
puede abrirla. Cuando el core arranca solo al iniciar sesión, esa ventana puede quedar detrás de otras, o aparecer sin
nadie frente a la computadora.

- Elegí **Permitir**. APX lee el proyecto apenas respondés; no hace falta nada más.
- Mientras nadie responde, APX arranca y funciona como siempre. Los ajustes de ese proyecto dicen que su carpeta
  todavía no se abrió, y sus agentes no trabajan en su carpeta; tus otros proyectos siguen igual.
- Si elegiste **No permitir**, o la ventana ya no está: abrí **Ajustes del Sistema › Privacidad y seguridad › Archivos
  y carpetas**, activá la carpeta debajo de “node” y reiniciá APX (`apx service restart`, o salí y abrí la app de
  escritorio).
- Para que no pregunte, guardá los proyectos en una carpeta que macOS no protege, como `~/work/…`.

Antes de la 2.12.4 el core esperaba la respuesta para arrancar: la app de escritorio se quedaba en **Conectando con
APX** y `apx status` no encontraba ningún core hasta que alguien respondía la ventana.

## El puerto ya está en uso

Un solo proceso puede escuchar en el `7440`. Si otro core ya lo tiene (un `pnpm dev` de antes, el core de la app de
escritorio, el servicio), un segundo core no arranca. `apx service install` lo revisa antes y te lo dice:

```text
a core already answers on http://127.0.0.1:7440 and it is not the service's. Stop it first (it may be `pnpm dev` or the desktop app), then run install again.
```

Frená el otro, o dale a este core otro puerto con `APX_PORT` (la terminal también sigue a `APX_PORT` y a `core.env`).
La app de escritorio no se pelea por el puerto: si ya responde un core en el `7440`, usa ese.

## "Missing or bad token"

Cuando el core está expuesto (red local o Tailscale) tiene un token, y cada pedido lo necesita, o la llave de un
dispositivo vinculado. El comando `apx` y la app de escritorio en la misma máquina lo leen solos de `<home>/core.env`.
Si ves `APX · unauthorized` con `missing or bad token`:

- Estás usando otra carpeta que la del core: revisá `APX_HOME`, o pasá `APX_TOKEN` a mano.
- Estás en otra máquina: no copies el token, vinculá (`apx pair` en el servidor). Un navegador muestra **Vinculá este
  dispositivo**.
- El dispositivo fue revocado: vinculalo de nuevo.

Dos más que podés cruzarte si cambiás el acceso a mano:

- El core no arranca con `refusing to listen on 0.0.0.0 without APX_TOKEN`: un `APX_HOST` que no sea loopback siempre
  necesita token. `apx expose lan` te crea uno.
- `a request through a proxy needs APX_TOKEN on the core`: algo (como `tailscale serve`) le reenvía pedidos a un core
  sin token. `apx expose tailscale` crea uno.

## Un cambio de acceso no se aplicó

El core lee `core.env` solo al arrancar. Después de `apx expose`, corré `apx service restart` (el panel reinicia su
propio core cuando puede, o te dice **Guardado: se aplica cuando el core vuelva a arrancar**). `apx status` muestra
`Restart needed` mientras el acceso guardado no coincida con el que está corriendo.

`apx expose status` también te dice si una variable de entorno está pisando el archivo (por ejemplo `the environment
overrides: APX_HOST`): las variables del proceso siempre ganan.

## Un código de vinculación no anda

| Lo que ves | Por qué, y qué hacer |
|---|---|
| "Ese código es incorrecto o venció" | Los códigos duran 10 minutos y sirven una vez. Reiniciar el core también los anula. Pedí uno nuevo. |
| "Demasiados códigos incorrectos" | Cinco códigos mal pausan la vinculación por cinco minutos. Esperá y pedí un código nuevo. |
| "Tu teléfono todavía no llega a este core" | El core solo escucha en su propia compu. Exponelo (red local o Tailscale), reinicialo y vinculá de nuevo. |
| El teléfono no conecta para nada | No está en la misma red (red local) o en tu tailnet (Tailscale), o la dirección está mal. Probá la dirección en el navegador del teléfono. |

Más en [Tu teléfono](/es/devices/phone/).

## Un canal no responde

```bash
apx channels          # el estado de cada canal y su último error
apx channels outbox   # lo último que se mandó: queued, sending, sent, uncertain o failed, con el error
apx pairing           # desconocidos esperando tu aprobación
```

- **Un desconocido no recibe respuesta**: por defecto, una persona nueva recibe un código de vinculación y te espera.
  Aprobala con `apx pairing ok <code>` (o `apx pairing me <code>` si sos vos desde otra dirección), o decíselo a tu
  secretaria.
- **Tu propio mensaje parece no llegar a ningún lado**: por defecto, lo que escribís en un canal va al chat Home, así
  que la respuesta también está ahí.
- **Una persona está bloqueada**: las personas bloqueadas no reciben respuesta. Revisá `apx contacts`.
- **Un envío quedó `uncertain`**: el core se cortó mientras mandaba, así que no puede saber si llegó. No se manda dos
  veces.
- **Dos APX contestan el mismo bot**: no corras APX v1 y v2 con el mismo bot. Por eso instalar v2 frena el daemon de v1.

Más en [Canales](/es/channels/overview/).

## Errores de modelos

```bash
apx models            # cada motor, y "(not available)" con el motivo cuando no se puede usar
apx models --refresh  # les vuelve a preguntar a los motores
apx models config     # el predeterminado, la cadena del router y sus reglas
```

- **Un motor no está disponible**: casi siempre falta una clave o un inicio de sesión. Cargalo en **Configuración ›
  Motores y modelos**.
- **El router no pasó al siguiente**: pasa al próximo modelo de la cadena solo cuando un modelo falla **antes de que
  corra alguna herramienta** en ese turno.
- **Un modelo tarda mucho en empezar a responder**: el core espera 45 segundos el primer byte (`APX_LLM_TIMEOUT_MS`).

Más en [Modelos](/es/concepts/models/).

## Falla un servidor MCP

```bash
apx mcps                    # cada servidor, su estado (ready, needs-approval, error…) y su error
apx mcp check <server>      # una prueba de conexión: OK o Failed, el tiempo y la cantidad de herramientas
apx mcp tools <server>      # lo que ofrece
```

<Terminal command="apx mcp check notes">{`notes: Failed · 3012 ms · 0 tools
connect ECONNREFUSED 127.0.0.1:3000`}</Terminal>

- **needs-approval**: un servidor del `.apc/mcps.json` de un proyecto corre recién cuando confiás en esa definición
  exacta: `apx mcps trust <project> <server>`.
- **needs-sign-in**: pidió que inicies sesión en tu navegador y te espera; APX no lo vuelve a arrancar solo. Tocá
  **Iniciar sesión** en **Recursos › MCP**, o corré `apx mcp signin <server>`.
- **Falta una clave**: los servidores MCP reciben sus secretos por referencia; cargalos en **Recursos › Variables**.
- **Ambiguous server**: el mismo nombre existe global y en un proyecto. Sumá `--project <id>` y `--scope`.

Más en [Servidores MCP](/es/extend/mcp/).

## El navegador necesita la app de escritorio

Los agentes manejan el navegador que presta la app de escritorio. Sin la app, el core usa su propio Chrome sin
ventana, que no te puede pasar el control y nunca usa tus sesiones iniciadas. Errores que podés ver:

- `no connected node offers "browser" (open the APX desktop app)`: abrí la app de escritorio en la compu donde corre
  el core, o una conectada a él por SSH. Una app conectada **por dirección** todavía no presta su navegador.
- `no Chrome, Chromium or Edge on this machine`: instalá uno para el navegador sin ventana, o apuntá `APX_CHROME` a él.
  `APX_HEADLESS=off` lo apaga.

Para leer páginas y buscar, los agentes también tienen `web_read` y `web_search`, que no necesitan navegador. Más en
[Navegador](/es/office/browser/).

## APX v1 y v2 a la vez

No se pisan:

| | APX v1 | APX v2 |
|---|---|---|
| Puerto | `7430` | `7440` |
| Datos | `~/.apx` | `~/.apx/v2` |

v2 nunca escribe los archivos de v1. Instalar v2 con el script frena el daemon de v1 y saca su comando `apx`, porque
los dos contestarían en los mismos canales; los archivos de v1 quedan para que los importes con `apx import-v1` o con
la configuración inicial (solo lee v1). `apx daemon` es una costumbre de v1: en v2 te explica los comandos `apx service`.

## Empezar de cero sin perder nada

Para probar algo riesgoso, arrancá un segundo core con su propia carpeta, su propio puerto y los secretos en un
archivo, así nada toca tus datos reales ni tu Llavero:

```bash
# Desde el código
APX_HOME=~/work/apx-scratch APX_PORT=7460 APX_SECRETS=file pnpm dev

# Desde un paquete instalado
APX_HOME=~/work/apx-scratch APX_PORT=7460 APX_SECRETS=file \
  ~/.apx/v2/app/current/node/bin/node ~/.apx/v2/app/current/apps/core/src/main.ts
```

Después apuntá la terminal a ese core:

```bash
APX_HOME=~/work/apx-scratch APX_URL=http://127.0.0.1:7460 apx status
```

Un core con su propio `APX_HOME` tampoco toca las skills de Claude Code, Codex y Cursor. Cuando termines, borrá la
carpeta de prueba.

<Aside type="caution">
No borres `~/.apx/v2` para "resetear" APX: ahí están todos los agentes, chats, tareas y notas, y en un servidor también
la app instalada. Mové las cosas a un costado, y solo con el core frenado.
</Aside>
