Tasks are the office's to-do board, shared by you and your agents. You create them, agents create them, and giving one
to an agent is enough for it to start. **Tasks** in the sidebar shows them from every project; each project has its
own **Tasks** tab with **New task**.

<Shot name="tasks" alt="The Tasks screen with groups In progress, Pending, In review and Needs your review, each listing tasks with assignee and due date" caption="Tasks, across every project" />

Before creating another task, agents are instructed to check the open tasks and continue an existing task when
it already covers the same or closely related work. This is not automatic duplicate detection. For a task that
changes code, see [where the code work goes](/office/code/#where-a-task-changes-code).

## Recording versus starting work

Ask for an action and the agent should do it with its tools, or hand it once to the needed specialist—not substitute
board updates for a result. Long work can use a task for internal tracking, but it must actually start and report a
result or a concrete blocker.

To record an idea without starting work, ask for a capture-only task and leave it **unassigned**. A task with an
assignee and a description starts its own work session unless it is proposed, scheduled for later or paused by
agent limits. Assignment and delegation are alternative ways to start work, not two steps to perform together.
Within one turn (including a restart recovery), APX prevents mixing task execution and delegation for the same
teammate and project, even when the wording differs. Genuinely different work can use the delegation tool's explicit
`independent` flag and a brief naming the separate outcome; it is not for retries or the same goal. This distinction
is recorded with the delegated run. The guard is not semantic duplicate detection across chats or later turns, and
it cannot verify that an agent's claim of independent work is correct.

## What a task has

| Field | Values |
|---|---|
| **Type** | **Task** (work in a project), **Commitment** (something promised with someone) or **Errand** (something small to do on the way: buy, call, pick up). |
| **Column** | **Backlog** (just arrived, new tasks land here), **To do** (decided, it is next), **Doing** (someone is on it now), **Review** (finished, waiting for a check). |
| **Priority** | Urgent, High, Normal, Low. |
| **Who does it** | An agent, or nobody. Picking a project's agent puts the task in that project. |
| **Due date and reminder** | When it is due, 1 hour before, 1 day before, another time, or no reminder. |
| **Tags** | Free words (`client`, `launch`…). |

**Done** and **Drop** close a task; **Reopen** brings it back. The filter at the top switches between **All**,
**Tasks**, **Commitments** and **Errands**. On the Tasks screen, the project picker beside it narrows the list to one
project or shows **All projects**; this browser remembers the choice for the next visit.

### How the list is grouped

- **Proposed** (when there are any, on top): tasks an agent proposes and nothing starts until you accept them.
  **Accept all** in its header, or **Accept** and **Drop** in each one's drawer. See
  [Proposals](#proposals).
- **Needs your review** (first): what is yours. An agent asked you something or needs your decision (it goes on when
  you answer; you also mark it so with **Waits for your answer** from its menu), or a finished task you review to
  close. Each row says which: **Asks you something** or **Reviews: You**.
- **In progress**: its column is Doing, or an agent is working on it right now.
- **Pending**: Backlog or To do, nobody started it yet.
- **In review**: finished, and the agent you named reviews it (**Reviewed by** in the drawer, or an agent naming one).
  It is asked to review at once: asking for changes sends it back to whoever did it; approving makes it yours.
- **Closed recently**: done or dropped, newest first.

### Group existing tasks as subtasks

Ask your agent to put related tasks under an existing parent task. Both
must be in the same project. This keeps their IDs, history, comments, sessions and assignees; grouping alone does
not start work again or change whether a task is open or closed. Unrelated tasks stay separate.

The CLI equivalent is `apx tasks edit <id> --parent <parent-id>`; `--parent ""` detaches the task. The agent's
`task_update` tool and `tasks.update` protocol method accept `parent` (an existing task ID, or `null` to detach).
An agent can move a task beside or below others, never higher up: detaching it or moving it toward the top is yours.
A task cannot become its own parent or sit below one of its descendants. The list nests tasks when both the parent
and child are present in the current filter; opening the parent also lists its subtasks.
Detach a child before moving it to another project (or detach and move it in the same update). Detach all
subtasks before moving their parent. Creating a subtask also requires the same project as its parent. Work your
agent hands to another project's agent from a global task's chat stays listed under that task, and a subtask
already linked that way can still be edited.

## Attachments and task chat actions

Tasks can keep selected screenshots and files as independent snapshots, when created or later. The task shows them as
same-size squares: a picture's thumbnail, or a file's name and size. Click one to open it (pictures in a viewer you can
step through, text and PDFs in a reader, anything else downloads); hover it to download or remove it. Removing always
asks first. Each task holds up to 50 files, at most 20 MB each. Deleting the original chat does not delete
the task's copy; removing the attachment deletes that copy, not copies already shared elsewhere. Authorized agents
can inspect task attachments without gaining access to private contact chats. Sending a file outside APX remains
a separate owner action.

Use the task chat group's actions button or right-click menu to change its column, mark it waiting, close or reopen
it, or archive its chats. Archiving preserves history: it does not close the task or restart work. Task status appears
beside the chat header, and the opening task description preserves paragraphs and lists.

## Assigning starts the work

Give a task to an agent (when you create it, or later) and it starts working right away, in **its own chat for that
task**. That chat is a normal chat listed in the Inbox: you can open it and watch, or talk to the agent there.

<Steps>

1. Lucía creates "Write the shipping rates page" in Acme Store and picks **Tomás** in **Who does it**.
2. Tomás's chat for the task opens with the task's words and he starts: reads the project, drafts the page.
3. His answers stay in his chat, and how far he got shows in his plan. He comments on the task when his plan is done
   or to ask someone something. The task keeps those comments; the chat keeps the work itself (every tool call,
   every file). When he closes the task, his last answer is posted as his report.
4. When he needs a decision, he asks you. The task moves to **Needs your review** until you answer.

</Steps>

Open a task and its drawer shows the description, the fields, the **Comments** and the **History** (who created,
moved, assigned or closed it). **Sessions** at the top counts the chats the task was worked in and opens their list,
to jump to where the work happens. If you reassign it, the new agent gets its own chat and is told who worked on it
before, and where to read it.

### Goal, what you asked and the plan

Above the description, a task shows where its work must arrive and what you said about it:

- **Goal**: one or two lines with the result you will check ("computer use moves like the reference, with one cursor
  per agent"). An agent that hands a task to another one must write it; you can edit it in the drawer. The agent
  working the task reads it first, every turn.
- **What you asked**: when an agent creates a task for you, or changes it, while answering you, APX keeps your
  message as you wrote it, with the one or two you sent just before it. The agent working the task reads your words
  before the description, which is the other agent's summary of them; where the summary asks for more than you said,
  or for the opposite, your words win, and when it is not clear the agent asks you.
- **Plan**: before working, the agent writes its steps toward the goal and marks each one pending, under way or done
  as it goes. The drawer shows them as a checklist with how many are done, and so does the task's chat, under the
  agent's message ([The agent's plan](/office/chat/#the-agents-plan)). When the work stops leading to the goal,
  the agent tells you what is missing instead of going on.
- **A pause when it gets nowhere**: if the agents on a task take 12 turns or 2 million tokens without finishing a
  step of its plan (counted since the last step done or since you last wrote), they pause. You see why in the chat,
  with the button to let them go on, and once in your notifications. A step done, or your message, starts the count
  over.
- **One agent does the work, one review at the end**: the agent on a task does it itself. It asks another agent only
  once the rest of its plan is done, usually for a review (unless you ask it for help sooner). Work for someone else
  becomes a subtask. The reviewer answers Approved, Approved with notes, or Blocked with the one thing that blocks it.
  Notes never block.
- **Few comments**: an agent comments on a task when its plan is done, to ask you or a teammate something (an
  `@name`), or when it answers you; at most once a turn, in short lines. Progress shows in the plan. A helper answers
  whoever asked it, not the task.
- **Cleaning old tasks**: tasks from before 2.13 may hold dozens of progress comments. Your super-agent offers to
  clean them: it tells you what it would take out of each task and the one summary it would leave, and removes
  nothing until you say yes. Your own comments always stay.

The description reads as formatted text (lists, bold, links); the pencil opens it to edit.

<Shot name="task-drawer" alt="A task open in its drawer: title, assignee, priority, and a conversation of comments from the owner and an agent" caption="A task's drawer: comments, fields and the work chat" />

Assigned tasks that never started are picked up on their own: once an hour, the most pressing few get started, as
whoever gave them: a task an agent gave counts against that agent's limits, never as your own request. To
have one start later (tomorrow morning, after a release), set **Starts** in its drawer, or `apx tasks add … --start
2026-10-23T09:00`: its agent starts then, not when you assign it.

### Moving the current work into a task

**Since 2.11.1**, when an agent immediately assigns its current work to itself as a new
task, APX transfers execution to the task's chat. The originating turn stops executing tools; the task chat gets a
bounded handoff of the request and recent findings so it can continue rather than repeat the investigation.
This does not prohibit unrelated parallel chats. If the current turn already has helpers or other active work,
or cannot transfer safely, APX refuses the handoff and the agent must continue there, not start a second executor.

### Comments and @mentions

Write in the task's **Comment** box. A comment that names no one waits a minute (so you can add another) and then
goes to the task's agent, or to the super-agent when nobody has the task; its ticks show it sent, delivered and read.
An `@name` asks that agent: it answers in its own chat for the task, and its
answer comes back as a comment. Ask Vera from Lucía's task:

> @Vera can you have the product photos by Thursday? This page needs them.

An agent asks a teammate the same way: its `@name` in a comment opens a consult on the task, shown as a card with
the question and the answer, and the answer comes back to the agent that asked, which goes on with its work. One
comment asks two teammates at most, and the one answering a consult cannot ask anyone further. An agent can also
mention you to get your attention.

Whoever asks the same teammate again (you, or the same agent) goes on in that consult, with what the teammate already
knows, and the task shows a new card for the new answer. If the teammate is still working on an earlier question, the
new one opens a consult of its own, so questions asked together stay apart.

### An agent works a task until it is done

When an agent's turn on a task ends with the task still in progress (it ran out of steps, or stopped at "I'll
continue"), its next part starts at once, numbered, up to nine. It stops when the agent closes the task, marks it
waiting on you with what you must do, says what blocks it, or when a part got nowhere. Closing its own work as done,
an agent must say what it verified.

### When an agent's task closes

A task one agent created and gave to another reports back when it closes. Your main agent hears of every task its team
closes, also the ones you or another agent gave, and tells you what came of it. Your main agent can hand a whole goal to a
project's orchestrator as a task; when the orchestrator closes it, hours and restarts later, your main agent gets
its report in the chat where it created the task and tells you what matters. Closing a task yourself, or an agent
closing its own, wakes nobody. That turn counts toward the [turns agents start on their own without
you](/concepts/agents/): past the limit, the report waits until you write in that chat.

### Requesting corrections

Reopening alone does not start work. To reject a delivery and ask the same assignee to correct it, an agent uses
`task_close` with `state: "open"`, `rework: true`, and a `note` explaining the corrections. Protocol clients use the
same fields on `tasks.close`.

The task must be closed and assigned. The request keeps its identity, column, history and work chat, records the
reason and new run, and reports back to the original coordinator when the assignee closes it again. Requests are
refused without changing the task if work is still active or agent limits are paused; wait for work to finish or
ask the owner to allow the chain to continue, then retry. Ordinary updates and administrative reopening never
start a correction run.

## Sub-tasks

A task can name a parent task, so "Spring launch" can hold the photos for Vera and the rates page for Tomás.

The list nests them under their parent. A task an agent creates while it works on a task is a sub-task of that one:
the agent that owns a task carries it end to end, and hands a part to another agent through a sub-task, not a chat.

### Proposals

When an agent finishes, it may see more work: a QA pass, a review, something for another area. Work its own role
hands out it creates and starts; the rest it **proposes**. A proposed task waits in **Proposed**, with who proposed
it, until you accept it (it starts like any assigned task) or drop it. You get one notice per agent with how many it
has waiting.

To accept just one open proposal, right-click it and choose **Accept**, or use **Accept** in its drawer.
Opening or dismissing the menu changes nothing.

**Accept all** asks you to confirm the number of proposals in the current list, including those behind **See more**.
Only confirming accepts them and lets assigned agents start; cancelling or closing the dialog changes nothing.
Proposals that arrive while the dialog is open are not included. Before accepting, APX checks the selected proposals
again. If that check finds one changed or no longer available, acceptance does not start: review the list and try again.
Acceptance runs one proposal at a time. If it stops or a response is lost, some proposals may already be accepted;
check the updated list before trying again. An error message counts only acceptances whose responses were confirmed.

Some tasks are proposals whatever the agent asks for. When you ask your super-agent for several things without saying how, it asks
you first (a plan, one task each, or doing it itself); once you said how, it goes ahead.

The proposals:

- **A hand-off chain three deep.** A sub-task of a sub-task of a sub-task is proposed, so agents cannot keep passing
  work down on their own.
- **Work given back up the chain.** A sub-task for an agent that created one of the tasks above it is proposed, so two
  agents cannot ping-pong the same work.

For an existing task you explicitly assigned or accepted, APX can verify its current executor and
recorded hand-offs instead of counting its historical parents. Up to three actual forward hand-offs may continue;
an independent review may return to its direct sender for up to two rounds with the same author and reviewer. The
handoff must explicitly request **Review**, and APX starts that separate agent with a review assignment. A previous
Review status alone does not establish a review round. A third round, a changed review pair or unrelated work sent
back up the active chain waits for you. This does not accept a proposal already waiting.
Your follow-up messages in the task conversation or its current agent's work chat keep the same assignment and do not
reset these limits. A pending message keeps the authorization it had when it arrived, including after a restart;
revoking or replacing that assignment does not authorize the old message again.

The authorization must still match the task, its executor and its project. Clearing its assignee, changing its scope
or pausing it for your decision prevents this continuation. That includes an agent rewriting its title, description or
goal, even in the same change that hands it on: the new scope waits for you as a proposal. Setting a goal the task
never had is not a rewrite. If a recorded owner assignment can no longer be verified,
APX proposes the hand-off even for a task without historical parents. Tasks without a recorded owner assignment keep
the parent-chain rules above: an unassigned task with no owner authorization cannot bypass those rules as an authorized
continuation. Ordinary assignments that already passed those rules are unchanged. The orchestrator's chat is not authorization by itself: the task must belong to it and its execution must
be linked to your current assignment. Accept the proposal yourself when you want it to start; removing historical
parents is not an authorization step.

### A reviewer or a new assignee?

To ask for a review while keeping the same responsible agent, move the task to **Review** and choose an independent
agent in **Reviewer** (or ask your agent to set it). APX opens a review consultation, for at most two rounds: requested
changes go back to the responsible agent; an approval is brought to you. Approval does not automatically restart the
responsible agent for delivery. A proposed task starts no review until you accept it.

Changing the **assignee** instead transfers responsibility and starts a task work session. That is the hand-off
covered above, not the review consultation. Your review gate and the agents' budgets still apply.

## Commitments

A commitment is a task with **a person** (one of your [contacts](/channels/overview/)) and **who owes it**: **I owe it** (you promised something to someone) or
**They owe me** (someone promised something to you). It has a due date like any task, so it is reminded and raised
before it is late.

<Shot name="commitments" alt="Tasks filtered to Commitments: what you owe each person and what each person owes you, with due dates" caption="The Commitments filter" />

A commitment ends one of three ways, or gets a new date:

| Action | What it records |
|---|---|
| **Kept** | Delivered. Closes it as done. |
| **Missed** | Its date passed undelivered. Closes it. |
| **Release** | Released by agreement. Closes it. |
| **New date** | Renegotiated: it stays open with the new date, and a counter shows how many times it moved. |

Only your word settles a commitment. Agents never mark one kept or missed on their own: the day-close routine asks you
how they went, and the agent records your answer (see [Secretary](/office/secretary/)).

## From the terminal

<Terminal command="apx tasks help">{`apx tasks [--project p]                 Open tasks by column
apx tasks add <title…> [--project p] [--agent a] [--person name --owed me|them] [--due 2026-10-05]
apx tasks commitments                    What you owe and what you are owed
apx tasks move <id> <column>
apx tasks done|drop|reopen <id>
apx tasks say <id> <text…>               Comment; @agent asks that agent there`}</Terminal>

A few examples (agent and project ids are the ones `apx agents` and `apx projects` print):

```bash
# A task for Tomás in Acme Store: he starts on it at once
apx tasks add Write the shipping rates page --project <acme-id> --agent <tomas-id>

# You promised Marta (a contact at Northwind) a quote by Friday
apx tasks add Send the wholesale quote --person Marta --owed me --due 2026-10-10

# Move it, comment on it, close it
apx tasks move <task-id> review
apx tasks say <task-id> @Lucía please check the copy before Friday
apx tasks done <task-id>
```

Columns for `move` are `backlog`, `todo`, `doing` and `review`.

<Aside type="note">
Agents can open, move, comment on and close tasks with their own tools, so "Lucía, put that on the board for Tomás"
works in any chat.
</Aside>

## Agent tools

- `task_list` lists the board; `task_get` reads one task by its `task` ID.
- `task_get` includes task fields, history, work sessions, consults, subtasks, token usage and the latest 60 conversation messages. Saved evidence (file references, change patches and consult summaries) stays with its message; it does not fetch attachment bytes or invent missing proof.
- Detail sections are bounded for the model, with omission markers for long content and older comments. Task and conversation content is returned as data, not instructions.
- Project agents can read their project's and global tasks, not other projects' tasks or related work. Missing and out-of-scope IDs return the same safe error. The global secretary keeps its board-wide visibility.
- `task_create`, `task_update`, `task_comment` and `task_close` create and maintain tasks; `commitment_settle` records an agreed commitment outcome.
- `plan` keeps the agent's checklist; in a task's chat it is the task's plan.
