A routine is work an agent does on its own, on a schedule: a stock check every weekday morning, a look at open pull
requests every hour, a weekly summary for a client. You hear back only when there is something to say.

Routines live in each project's **Routines** tab (Home's are in the base project). **New routine** opens the editor.

<Shot name="routines" alt="A project's Routines tab: each routine with its flow, a row of 14 activation bars and its next run" caption="Routines, with their last activations" />

## Actions

Each routine does one of four things:

| Action | What happens |
|---|---|
| **Agent** | An agent (Home or one of the project's) answers your prompt. It tells you only when it has something to say. |
| **Message** | Sends you a fixed message on your channel (Telegram, WhatsApp…). No model. |
| **Shell** | Only runs a command in the project's folder. No model, no notice. |
| **Watcher** | Sweeps your work for what is worth a word (late tasks, commitments coming due, quiet projects, tasks set up so they cannot move) and calls the model only when something is new. |

In the unreleased integration branch, **Team news** and **Important mail** are [secretary capabilities](/office/secretary/), switched on or off in **Settings → Super-agent**, not routine actions. Existing customized instructions and scheduled history are preserved.

## Schedules

| When | Example |
|---|---|
| **On a schedule** | Pick days and time ("Weekdays at 08:30"), or **Write a cron**: five fields, in your local time. `30 8 * * 1-5` is weekdays at 08:30. |
| **Every** | Every N minutes, hours, days or weeks. At least 5 minutes. |
| **Once** | A single date and time. |
| **By hand** | Only when you press **Run now**. |

A run missed while the core was off runs once when it comes back, never twice.

## Flows

In the unreleased integration branch, open **Flows** in the global sidebar beside **Tasks** and **Resources**. The list
shows every flow across projects with its steps, how many of them use AI, a bar for each of its last runs and an
on/off switch; the project menu narrows it. The Routines tab's shortcut opens this same global screen. Direct links use
`#view=flows`, `#view=flows&scope=<project-id>`, `#view=flows&flow=<flow-id>` (its runs) or
`#view=flows&flow=<flow-id>&edit=1` (its editor); chat buttons may use `apx:flows`, `apx:flows/<project-id>`,
`apx:flows/<project-id>/<flow-id>` or `apx:flows/<project-id>/<flow-id>/edit`.

**New flow** opens the editor, blank or from a starter shape. Add steps from the left (they join after the step you
chose), drag from a step's output dot to join two steps, and set each step at the right:

| Step | What it does |
|---|---|
| Incoming webhook | Starts the flow when a service sends a POST. Its address appears once the flow is saved. |
| Schedule | Starts the flow at set times: **Every 5 min**, **Every hour**, **Weekdays 08:30**, **Daily 03:00** or a cron expression (minute, hour, day, month, weekday), in your time zone. The side panel shows the next runs. |
| Check | Compares a field of what arrived with a value (`form.tier` is `A`). Steps joined to its **Yes** dot run when it matches, steps joined to **No** when it doesn't. No model. |
| Read table | Brings saved rows into the run. No model. |
| Save to table | Keeps what arrived, a field of it or an earlier step's result under a key. No model. |
| AI model | Gives a task to an agent of the crew, with what arrived or an earlier step's result. Spends tokens. |
| Routine | Runs a manual routine of the project. |
| Direct model | Asks one set-up model once, without tools, and passes its answer on. Spends tokens. |
| Outgoing webhook | Calls a URL with GET, POST or PUT. Headers and body can carry values of the run; a key goes in a header as `secret://name`, from **Secrets**. Later steps read its answer as `$steps.<step>.status`, `.ok` and `.json` (or `.body` when it isn't JSON). |
| Notify | Sends a message as you on one of your chat apps (Telegram, WhatsApp, Discord…) to someone you know there, to yourself, or to a room you listed. With **Only if there's something to tell**, it doesn't send when every value in the message came out empty. |

A flow has one trigger. SQL and Cmd show as **Soon** and can't be added yet. A flow runs as drawn: steps
can branch and join, and each step can receive what arrived or the result of a step before it. In **Goes on to** a
check's **Yes** or **No** chip switches that connection to the other branch. The side panel says *Runs as drawn*, or
why the drawing can't run yet (an agent outside the project, a model that isn't set up, two saves to one key with no
order between them, a schedule more often than every 5 minutes), also for a new flow before its first save.

**Save** keeps your drawing. When the flow is on, saving also makes it what runs: new events use it, and events already
received finish with the version they started with. When the flow is off, turning it on makes your last saved drawing
what runs. A flow whose drawing has the old one-path shape (webhook, checks, read, save, then one agent or routine) keeps
running as before until you save a drawing it can't stand for. **Try a run** follows sample data through the checks
and branches and marks the steps it would reach, without saving, reading a table, sending or calling an agent; a step
that needs another step's answer says it depends on it. Saving never runs anything, and a new flow starts off.

Opening a flow shows its steps as they ran in the chosen run (numbered, green when they ran, dashed when they didn't,
red when they failed), what each step got and gave, when it started and ended, a log, and the runs at the right with
their duration and tokens. A run made with an earlier drawing shows that drawing and says **Previous version**. A run
a check stopped marks that check **no** and the steps after it as not run. A step that handed work to an agent opens
its chat.

Each run has 10 minutes from the moment its event arrives; a model step has its own limit (up to 2 minutes). Steps that
call a model are sent once and never again: if APX stops or the answer doesn't come in time after the request went
out, the run says **Needs a look** instead of trying again, because the model may have done it anyway. Turning a
flow off stops new steps; a run that was waiting still ends at its time limit. A flow runs one event at a time, in the
order they arrived.

**Run now** on a flow's page starts it at once, through the same path as its trigger. A schedule flow runs with an
empty event; a webhook flow asks for the body it gets, filled in with the last one it received, and treats it like
any outside data. The run says **Started by you**. **Stop run** on a run that is going stops it: steps that haven't
started don't run, and a step already sent to a model is left as **Needs a look**, never sent again.

A schedule flow runs while APX is on. If APX was off at a run's time, the flow runs once when APX starts (not once for
each time it missed), and that run says it started late. If the last run is still going when the next time comes, that
time is skipped, not queued, and the flow's page says how many were skipped. A flow that is off doesn't run on its
schedule and, turned on again, starts counting from then. A schedule flow has no address: it never takes a POST, and a
webhook flow never runs on a timer.

### Messages and calls a flow makes for you

A message, a room and a person are written into the step's text with placeholders: `$trigger.email` is a field of what
arrived, `$steps.<step>.text` the answer of a step before it (the **Add** buttons under the message put them in), `$$` is
a dollar sign. What arrived only fills the words: who gets the message is the person or room you picked, never one the
data names.

Because a notify step speaks as you and an outgoing webhook acts on another service, the first time a drawing would
send or call somewhere new, saving it while on (or turning it on) asks **Let this flow act for you?** and lists each
person, room and host. **Allow** makes it what runs; **Not now** keeps the previous version running. Each run then
sends without asking again.

Each send and each call that changes something goes out once: if APX stops or the other side doesn't answer after it
went out, the step says **Needs a look** instead of repeating it (check the chat or the service). A GET, which changes
nothing, tries once more if the connection fails before any answer. A flow sends at most 20 messages an hour, and makes at most 60 calls that
change something; the next one fails without going out. A message to a chat app that isn't running is taken back,
not sent later. An outgoing webhook only calls addresses on the internet: an address on this computer or
a private network is refused, also when a name points there, and redirects are not followed. Its answer is kept up to
256 KB read (16 KB of text), files are only said, and a secret it used never shows in the run, only `secret://name`.

The CLI starts and stops runs too: `apx flows run <flow> ['<sample body JSON>']` and `apx flows stop <flow> <event>`.
They act as you, so they refuse to run inside an agent's command.

A Flow belongs to a project. Turn a webhook flow on before creating its token in
**Settings → Devices → Endpoints**. Public access is configured separately; it never exposes private RPC or the panel.

Send JSON such as `{"id":"order-42","data":{"status":"paid"}}` to `POST /flows/<id>` with that route's bearer
token. Keep the same event ID on retries. Empty, duplicate or nonmatching events do not call a model; matching work
uses the saved binding, not an identity or command chosen by the payload. Tables and event history persist across
restarts. A linked agent run can still fail, and external effects are not guaranteed exactly once. The panel shows
the last 50 runs at a time (**Show older runs** pages back) and up to 20 rows of the table; the private `flows.rows` and `flows.events` protocol methods provide paginated inspection.

Rotation invalidates the previous token immediately. If deleting its stored secret fails, a non-authorizing cleanup
reference survives for retry at core startup or the next rotation; the newly activated credential is still returned.
Interrupted token creation is tracked for the same cleanup. Restore the Secrets backend if rotations report a full
cleanup queue (1,000 references). Use the same idempotency key when retrying a management request whose reply was lost.

## Silence is an answer: SKIP

An agent routine's prompt is your own words. When there is nothing worth telling you this time, the agent answers
only `SKIP` and nothing reaches you. Write prompts that leave room for that:

> Check yesterday's orders for anything unusual: refunds over 200, a product selling 3× its average, a failed
> payment. If nothing stands out, answer SKIP.

## Commands before and after

**Add commands before and after** gives a routine a pre-command and a post-command. Both are shell commands you
write (agents cannot), run in the project's folder, two minutes at most and without credentials in their environment.

<Steps>

1. **Pre-command** runs first. Its output reaches the agent where you write `{{pre_output}}` in the prompt (or after
   the prompt if you don't), marked as outside data.
2. **Call the model** decides whether the agent runs, from the pre-command's result:

   | Option | The model is called |
   |---|---|
   | **Always** | every time |
   | **If it printed something** | only when the pre-command printed output |
   | **If it failed** | only when the pre-command exited with an error |
   | **Never** | never (the commands run alone) |

3. **Post-command** runs at the end with what came out, in these environment variables:

   | Variable | Value |
   |---|---|
   | `APX_LLM_OUTPUT` | What the agent answered (or the message) |
   | `APX_STATUS` | `completed`, `failed` or `skipped` |
   | `APX_SKIPPED` | `1` when the model was not called, else `0` |
   | `APX_PRE_OUTPUT` | The pre-command's output |
   | `APX_PRE_EXIT` | The pre-command's exit code |

</Steps>

That is how a routine spends **0 tokens** on quiet days: Tomás's pre-command lists the low-stock items, with **If it
printed something**, and the model is called only on the days there are any.

A **Message** routine uses `{{pre_output}}` too: "Today's weather: `{{pre_output}}`" sends the command's output as it
is, with no model at all.

## Anchors: always arrives

Routine news normally goes through your [interruption budget](/office/secretary/#the-interruption-budget): a daily
cap, gaps, quiet hours. Turn on **Always arrives** for a routine you never want held back, like a morning brief: its
news arrives even at night or past the cap, and does not count against it.

## Run now and the activation bars

**Run now** starts a routine immediately, whatever its schedule. Each routine shows its **last activations** as 14
bars, oldest to newest:

| Bar | Meaning |
|---|---|
| **The action ran** | It ran and had nothing to tell you. |
| **Told you** | It ran and sent you something. |
| **Skipped, 0 tokens** | The model was not called (the pre-command did not ask for it, or nothing new to watch). |
| **Failed** | The run failed. |
| **Did not run** | A time it should have run and did not. |

Each run is an ordinary chat of its own, so you can open it and see exactly what the agent did.

## From the terminal

<Terminal command="apx routines help">{`apx routines                                   Routines and when they run next
apx routines add <name> <prompt…> --agent a [--project p] (--cron "30 8 * * 1-5" | --every 60 | --at <ISO date>)
                 [--pre "<command>"] [--call always|output|fails|never] [--post "<command>"]
                                                The pre-command's output reaches the prompt at {{pre_output}}
apx routines run <id>                          Run now
apx routines on|off <id>
apx routines rm <id>
apx routines log <id>                          Recent runs`}</Terminal>

With no `--cron`, `--every` or `--at`, the routine runs by hand. `--every` is in minutes. The CLI creates agent
routines; message, shell and watcher routines and anchors are set in the panel.

```bash
# Weekdays at 9: Tomás looks at low stock, only when there is any
apx routines add low-stock "Here is today's low-stock list: {{pre_output}} Draft the reorder for the supplier." \
  --agent <tomas-id> --project <acme-id> --cron "0 9 * * 1-5" \
  --pre "./scripts/low-stock.sh" --call output

apx routines run <routine-id>     # try it now
apx routines log <routine-id>     # recent runs; "(nothing to say)" marks a SKIP
```

<Aside type="note">
Routines are yours: only you create or change them. An agent cannot schedule standing work for itself.
</Aside>
