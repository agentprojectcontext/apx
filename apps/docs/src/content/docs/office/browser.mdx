Agents browse the web in a real browser built into the [desktop app](/devices/desktop/). You watch every page live in
the chat's **Browser** side panel, and you can take the wheel at any moment.

## Watching an agent browse

When an agent opens a page, the chat shows a browser card and the **Browser** side panel follows the tab live: "Vera
is browsing · supplier.example.com". From the panel you can open the tab in a separate window or in your own browser.

> **You:** Vera, compare the shipping prices on our two carriers' sites for a 2 kg box to Córdoba.
>
> **Vera:** Opening both rate calculators… The first is 4.20 cheaper, but the second delivers a day earlier.

## Taking control

Press **Take control** on a tab and it is yours: click, type, scroll. The agent waits. **Give back** returns it.

The agent can also ask you to take over. When a site wants a login, a password, a 2FA code or a captcha, the agent
hands the tab to you ("Vera needs you to take over") and waits up to 5 minutes while you finish. Then it carries on
from the page you left it on.

<Aside type="caution" title="It never types your passwords">
The embedded browser refuses to type into password, one-time code and card fields, whatever the autonomy. An agent
either signs in with a variable you saved for that site (below) or hands the tab to you. Agents are also told never to
ask for passwords in chat.
</Aside>

Other fields: after the agent read a page, typing waits for your OK. In Auto it does not on a page your own computer
serves (`localhost`, `127.0.0.1`), such as the app it is building.

## When a page asks

Some pages ask through a box of their own: "Delete this item?", "Leave this page?", a name to type. The agent sees
the box when it reads the page and answers it, OK or Cancel, instead of getting stuck behind it. In the APX app the box
shows on your screen too and you can answer it yourself; once the agent answers, it goes away. While you have taken
control of the tab, its boxes are yours: the agent waits.

Pages in the APX app cannot ask you to type text in such a box (the app has never shown that kind). In APX's own
browser, used when the app is closed, the agent types the answer.

## Signing in with your saved passwords

An agent can sign in for you without ever seeing your password. Save it once and say where it is for:

<Steps>

1. In **Resources › Variables**, add the value as a variable (for example `ACME_PASSWORD`). For a username, save it
   the same way. For two-step codes, paste the setup key, or the `otpauth://` address, that the site offers for an
   authenticator app.
2. Open the variable's **Sign-in sites** and choose the field it goes into (**Password**, **Username** or
   **One-time code**) and the sites, such as `app.acme.com`. **Any site** lets agents use it on every website.
3. Ask the agent to sign in. It names the variable and the field; the browser fills it in.

</Steps>

On a site the variable is not for, the agent asks you first in the app: **Once**, **Always on this site** or **No**.
That card cannot be answered from a chat app such as Telegram, and **Always on this site** adds that site to the
variable, never "any site".

The agent gets back only "filled" or "refused". The value does not reach the model, the chat, the run's steps, the
core's logs or the pictures of the tab the agent looks at. The core keeps the value and hands it to the browser in
the same call. The browser sets the value on that very field, as typing would, from a place the page's own scripts
cannot reach, and checks these first:

- **The site:** the page's exact address (scheme, host and port), with no subdomain or look-alike. With **Any site**,
  any `https://` site qualifies; plain `http://` works only on your own computer.
- **The frame:** the field's frame must be on that same site. A field inside a frame from another site is refused.
- **The field:** it must be the kind the variable is for. A password never goes into a username box or a plain text
  field. Card fields are never filled.

While the page is open, snapshots leave the field's value out and pictures of the tab cover it, even if a "show
password" button reveals it. For as long as the tab is open, the value is also taken out of every page, address and
title the agent reads in it (a form that puts the password in the address, an error page that repeats it), and the
agent cannot run JavaScript in that tab (even with an earlier permission): open another tab for that.
Right after filling, the browser looks for the value elsewhere in the page (another field, an attribute, text or the
address). If the page copied it, the browser clears it everywhere, keeps that page from the agent until it moves on,
refuses the sign-in and tells you which site did it.

The core's log records each fill or refusal: the agent, the variable's name, the site and the outcome, never the
value. The variable's row shows the sign-in sites, and its **Sign-in sites** dialog shows where it was last used.
To revoke, remove a site or the variable: the next fill is refused. Sessions already open on that site stay open until
you sign out there.

Limits to know:

- A username is meant to be seen: pictures of later pages may show it.
- A script of the allowed site itself can undo the cover of a picture or copy the value onto a drawing: allow sites
  you trust.
- When the core runs on a server, the value travels to your desktop app over its connection to the core.
- With **Any site**, a page that misleads the agent can get the variable typed on a site you never named. Keep it for
  test accounts.
- Two-step codes from a saved setup key let the agent pass that site's second step without you.
- Signing in with saved variables works in the APX browser (desktop app or headless). It never works in an isolated
  computer, and it is not offered to outside apps through `apx mcp`.

## Editing a page an agent made

When an agent builds a site or a landing and opens it in the browser (a local address such as `localhost:5173`), you
can point at what you want changed instead of describing it. Press **Edit** in the browser bar:

1. Move the pointer over the page: the part under it lights up. Click a title, a button or a picture to pick it. Or
   pick it in **Elements**, the edit panel's list of every part of the page by what it is (title, text, button, link,
   picture, field) and what it says: pointing at a row lights that part up in the page.
2. The edit panel shows its fields: **Text**, **Text color**, **Background**, **Font size**, **Spacing**, and
   **Anything else?** for what you would rather say in words. What you change shows in the page right away, only in
   your view: the page's own code is untouched, and a reload brings it back as it was.
3. Click another part to edit that one, or go back to **Elements** with the arrow beside its name. **Your changes**
   lists only the parts you changed, numbered as on the page and marked **Changed**, and **Elements** marks them with a
   dot; a part you only looked at is not kept.
4. **Ask Vera** puts the changes in the chat's message box in plain words: the page, then each part by what it says
   and what to change. Add anything and send it; nothing is sent for you. **Discard**, or Esc, leaves the page as it
   was.

Edit shows on pages you can change: a file on your computer, or a page served from it or your local network
(`localhost`, `127.0.0.1`, `192.168.…`, a `.local` or `.test` name). A public site such as Wikipedia does not offer it.
It also needs the tab free or yours: while an agent drives it, take control first. A password, code or card field can
be picked but never read or changed.

> **You:** Changes to localhost:5173:
> - «Book a demo»: make it say «Get your demo»; font size 19 px
>
> Keep the orange.
>
> **Vera:** Done: the button reads "Get your demo", a bit bigger, still orange. Reloaded it for you.

## What agents do without JavaScript

Most of what agents used to ask JavaScript for, the browser does on its own, without asking you:

- **Where a link goes**: the page view an agent reads shows each link's address.
- **Rich text editors** (a post or comment box that is not a plain field) show as fields it can type in.
- **Lists**: typing in a drop-down list picks the option with that text.
- **Files**: typing the full path of a file in its folder or temp folder into a file field attaches it. It can only
  attach a file it may read; APX's own folder never.

JavaScript stays for what none of these covers, and it always asks.

## Approved JavaScript execution

An agent can use `browser_evaluate` in its existing APX tab. Supply either a JavaScript
expression in `script`, or a local `.js` `path` plus the SHA-256 of its exact bytes in `sha256`. File access follows the
agent's normal folder permissions; URLs are not script sources. VM chats accept inline code only, never host files.
Use an async IIFE for statements and return a value:
`(async () => ({ title: document.title }))()`.

Execution requires confirmation in the app (panel, Desktop or phone), even in Total; a shortened channel message
cannot approve it. Choose **Approve once**, **Allow in this tab**, or **During this turn**. Temporary consent allows new
scripts without another confirmation: it is not limited to the source shown on the first card. Both temporary options
are limited to the same agent, conversation and exact approved origin and are lost when the core restarts.
Tab consent expires after at most 30 minutes and also ends on closing, navigating or reloading the tab
(including same-origin reload), or reconnecting the browser. Turn consent lasts until this execution ends, with no
extra consent time limit; it does not last for the conversation. It can cover other tabs
only on that exact origin. It never applies to another agent, delegated session, future turn or routine. You can revoke
an active consent without waiting for it to expire. Denying a card grants nothing; a card whose waiting turn ended must
be requested again. These are not global tool permissions. In the panel or Desktop, open **Resources → Active browser permissions** to review and revoke them; on the phone, open **Active browser permissions** in the chat.

Supply the exact expected `origin` (for example,
`https://example.com`, without a path). The card shows tab, origin and full source; local files are snapshotted before
approval and execution uses those same bytes. Pass the `document` reference from the latest `browser_snapshot` too:
execution is bound to that exact Chromium context and URL, not just the origin. Navigation, reload, changed URL or another
snapshot invalidate that document reference; take a fresh snapshot, and approve again unless an applicable temporary
consent remains. A changed origin is refused before evaluating. Review the entire script
before approving: arbitrary JavaScript can read private page data or send requests as your signed-in account. The normal
typing tool's credential-field protection is **not a JavaScript sandbox**. Never approve code handling passwords, 2FA or
card data. The tab's profile and take-control/handoff rules still apply. This method is not exposed to outside MCP clients.

APX awaits promises and returns untrusted JSON text (up to 16,000 characters); undefined becomes null, bigint becomes text,
and circular or oversized results fail. Scripts are limited to 64,000 characters (files: bytes). APX stops waiting
for the Chromium evaluation after 7 seconds. A timeout is **not cancellation or rollback**: timers, requests or
other side effects may continue. Verify the page before retrying, especially after a send. This adds an agent tool, not a
new DevTools panel or remote debugging port. Desktop must load the matching new build; a core-only restart is not enough.

## Profiles

Each agent browses with one of three profiles, set per agent in **Settings › Agents** (or the agent's own panel):

| Profile | Cookies and logins |
|---|---|
| **Shared** | One profile shared by every agent that uses it. Log in once, all of them benefit. The default. |
| **Isolated** | A profile of that agent's own; nothing leaks between agents. |
| **Incognito** | Nothing is kept. Logins cannot be imported into it. |

## Importing your logins

If you are already signed in to a site in your own browser, there is no need to log in again in APX's.
**Settings › Browser** copies your sessions into the browser's shared profile: pick a source browser (Chrome, Brave,
Arc, Edge, Zen or Firefox), filter the domains and import only the ones you need. Your browser may ask for
permission; the values never leave your machine.

Agents can ask for this too. When a site wants a login, an agent can ask to use your session for that one domain. That
asks your OK every time (only total autonomy skips it), and agents try it before a hand-off.

## Without the desktop app

When no desktop app lends a browser (a server, or a Mac with the app closed), the core starts its own **headless**
Chrome, Chromium or Edge, without a window, on its first browser call. It browses the same way, but nobody can take
over there and your own logins are not used. `APX_HEADLESS=off` turns it off; `APX_CHROME` points it to a specific
browser.

## In your own Chrome

With APX's extension for Chrome, agents can also work in your own Chrome, where you are already signed in.

<Steps>

1. Install **APX** from the Chrome Web Store and open it from Chrome's toolbar: APX shows in the side panel.
2. Write there: "Roby, open the Northwind admin and tell me which orders are late."
3. The agent opens a tab in an orange tab group called **APX** and works in it while you watch. Chrome shows a bar
   saying that APX started debugging the browser.

</Steps>

- What you write in that side panel always uses your Chrome. Anywhere else (the app, your phone, a channel as you),
  agents use APX's own browser unless you ask for your Chrome ("do it in my Chrome") or a site needs your login: then
  they open a tab in the **APX** group, asking your OK first unless the agent's mode lets it act alone. A contact's
  message or a routine never reaches your Chrome.
- Agents see only the tabs in the **APX** group. To share a tab you already have open, drag it into the group; drag it
  out to take it back.
- **Cancel** on Chrome's bar stops APX in that tab at once; it stays yours until you drag it out of the group and back
  in. The agent opens a new tab if it still needs one.
- Passwords, one-time codes and card details are yours to type: agents refuse those fields and ask you to sign in.
  Page JavaScript and importing logins stay in APX's own browser.
- APX must be running on the same computer: it connects the extension by itself, in Chrome, Brave, Edge, Arc and
  Chromium on macOS and Linux. `APX_CHROME_HOST=off` turns that off.
- You do not need to open the side panel for agents to use your Chrome: the extension connects as soon as Chrome
  starts. If Chrome is closed when an agent needs it, APX opens it and waits for the extension; the agent asks you
  for help only if the extension is missing, turned off or does not connect.

<Aside type="note">
On Windows, agents cannot use your Chrome yet; the side panel works.
</Aside>

## From the terminal

`apx browser` drives the same browser from your shell, handy for scripts and for checking what an agent sees.

<Terminal command="apx --help">{`apx browser tabs
apx browser open <url> [--profile shared|incognito|agent:<id>] [--by <agent>]
apx browser nav <tab> <url>
apx browser snapshot <tab>
apx browser click <tab> <ref>
apx browser type <tab> <ref> <text> [--submit]
apx browser shot <tab> <file.jpg>
apx browser close <tab>
apx browser control <tab> user|idle|done
apx browser cookies                          List browsers whose sessions can be imported
apx browser cookies <source> [filter]        Domains with cookies (counts only)
apx browser import <source> <domain,…> [--profile shared|agent:<id>]`}</Terminal>

`snapshot` lists the page's elements with refs that `click` and `type` take. `control` sets who holds the tab.
`cookies` shows only counts, never values.

Outside apps such as Claude Code can use this browser too, through `apx mcp`. See
[Outside clients](/extend/outside-clients/).

## Computer use on macOS

Beyond the browser, agents can use your Mac's apps: look at the window in front, click, type and press keys. It is
**off by default**.

<Shot name="settings-desktop" alt="Settings, Desktop: quick chat shortcut, start with the computer, and the Computer use switch with Screen Recording and Accessibility permissions" caption="Settings › Desktop" />

<Steps>

1. Open **Settings › Desktop** and turn on **Let agents use this computer**.
2. Grant macOS **Screen Recording** (to see the window an agent works on) and **Accessibility** (to read a window's
   buttons and fields, click and type). **Open System Settings** takes you there.
3. Ask in a chat: "Tomás, open the label printer app and print today's 12 shipping labels."

</Steps>

While an agent uses the computer, the chat shows **What the agent sees**, a live view of the screen.

- Looking at the screen asks your OK, and so does every click, key and typed text. Under total autonomy none of them
  ask.
- Every 60 actions in one turn it stops and asks whether to go on, in every autonomy.
- It refuses password fields, and refuses a click where another app's window covers the point.
- A real click waits until your mouse is at rest, so it does not fight you for the pointer.

<Aside type="danger" title="Emergency stop">
**Stop** in the live view, or **⌘⇧Esc** from any app, ends every turn that is using the computer, right away. Ask
again whenever you want.
</Aside>

<Aside type="note">
Computer use is macOS only for now. Windows and Linux do not lend the capability yet.
</Aside>
